擁有者問了兩件事：還能多做哪些小工具，以及能不能把 OpenClaw、Hermes 這些大平台的 skill「接過來用」。這份只調查和規劃，不實作；每個結論標「已查證（附來源編號）」或「推測／未查證」，來源編號對到最後一頁。

結論：哪些可以不用再自己做

不用做 直接用別人的

GitHub PR／issue 摘要（GitHub 官方 MCP）、網頁轉文字（MCP 官方 Fetch）、git 唯讀查詢（MCP 官方 Git）。這三項本來在「小工具點子」裡，現在改成「接上去就好」。

不要再加功能 等改接官方

Notion、Todoist、Google 日曆三家都出了官方 MCP。SYNOX_Libs 這三個工具維持現狀、不要再加功能，等 SYNOX 能接官方 MCP（工作包 E3）之後，改成「接官方 MCP 的薄殼」。卡點：Notion 和 Todoist 的雲端版用 OAuth，SYNOX 現在不支援動態註冊（packs/oauth.py），接不接得上未驗證。

還是要自己做 外面沒有合用的

Windows 上的 Apple 提醒事項（外面的版本都只能在 macOS 跑）、繁中快速記帳（money）、本機 todo／notes／子彈筆記、Windows 效能監測、devlog。現成的都是「接別家 App」，或只能在 Mac 上用。

不建議裝

Windows-MCP（等於把整台桌面交給 AI）、OpenClaw healthcheck（會建議改防火牆，跟這台的規矩衝突）、「自我進化／自動更新」類 skill（會自己改指示或自己更新，跟這台「更新要人看過」的規矩衝突）。

兩邊的現況（2026-11-13 複查）：OpenClaw 約 394.4k 星，由 OpenClaw Foundation（501(c)(3) 非營利）維護，幾乎每週發一個穩定版（官方發版說明查到 v2026.11.1，11-05；二手部落格說 11-10 已經出 v2026.11.3）[S3][S38][S39]。Hermes Agent 約 263.1k 星，內建排程和長期記憶，接得上 MCP；查得到的最新版是 v0.21.5（2026-09-24），但只有二手來源，可能已有更新版 [S11][S40]。兩邊都內建定時排程（OpenClaw 叫 Automations、Hermes 是內建 cron）[S41][S11]，跟 SYNOX 的 /remind、/schedule 重疊，這部分不用再加強。

最重要的 5 個發現

  1. 名字查證了。「Open Cloud／Cloud bot」是 OpenClaw（龍蝦；MIT 授權、Node／TypeScript，GitHub 約 39.4 萬星）[S3]；「Hermes」是 Nous Research 的 Hermes Agent（MIT、Python，約 26.3 萬星）[S11]。兩邊的 skill 都是 SKILL.md 格式（agentskills.io 標準）[S1][S10][S13]——SYNOX 現在用的就是同一個格式（docs/pack-format.md「SKILL.md」）。所以「格式」不是障礙。
    推測 OpenClaw 的前身叫 Clawdbot、Moltbot：官方格式文件還收 metadata.clawdbot、.clawdhub 這些舊名當別名 [S1]，資安報導的網址也用這些名字 [S29][S31]，但官方 README 沒寫改名經過。也要分清楚：計畫書裡的「ClawBot」是你自己的本機專案，跟 OpenClaw 不是同一個。
  2. 真正的障礙是「執行方式」，不是格式。OpenClaw、Hermes、Claude Code 的 skill＝「說明書」＋「agent 本來就有的萬用 shell」：SKILL.md 叫 agent 自己去打指令 [S2][S17]。SYNOX 的 AI 沒有 shell，只能叫 pack.json 宣告過、標好危險程度的指令（src/synox/agent/tools.py）。所以別人的 skill 裡「去跑 gh pr list」這種內容，直接丟進 SYNOX 沒辦法用，得先轉成宣告過的 cli 指令。這是兩種不同的設計取捨：通用 shell 彈性大、能做的事多；SYNOX 選擇只開放宣告過的指令，代價是別人的 skill 不能直接用。
  3. 公開報導指出開放上傳的 skill 市集出現過相當數量的惡意 skill（這是開放上傳模式共同的難題）。2026 年的公開報導：Koi 稽核 2,857 個，抓到 341 個 [S25]；Snyk 掃 3,984 個，確認 76 個是惡意的，13.4% 至少有一個嚴重問題 [S23]；Unit 42 在 2026 年 6 月還找到 5 個躲過 VirusTotal 掃描的 [S24]。主要手法是在 SKILL.md 裡用文字叫人或 agent 先「安裝前置程式」（curl | bash、有密碼的 zip）。OpenClaw 自己也寫：「掃描乾淨不代表 skill 安全」[S9]。這類手法是整個 skill 生態（不分平台）共同的問題。SYNOX 的 AI 沒有通用 shell、危險指令要人按確認卡，可以降低其中「叫 AI 去跑」的那一半；「叫人自己貼指令」的那一半仍然擋不住（見 ADR 0022 的威脅 T3）。
  4. 最便宜的接法是 MCP，而且 SYNOX 兩頭都已經有一半。SYNOX 已經接得上 MCP 伺服器（kind: mcp，本機 stdio 和遠端 http 都可以），SDK 的 serve() --mcp 也能把 SYNOX 工具反過來變成 MCP 伺服器（docs/sdk.md）。MCP 在 2026-09 正式定案了「用 MCP 傳 skill」的擴充（SEP-2640），每個檔案都附 sha256 清單、內容改了就要重新核准 [S21][S22]，跟 SYNOX 鎖住 pack 檔案的做法同一個思路。你說的「雙向轉接」，用 MCP 加 SKILL.md 就能做成，不必自己另訂標準。
  5. 授權沒有問題；「把它們的開發者社群接過來」要打折看。ClawHub 上的 skill 一律是 MIT-0 授權 [S1]，Hermes 是 MIT，Anthropic 的 skills 是 Apache-2.0 [S18]，都能跟 AGPL 的 SYNOX 一起散佈。但 Hermes 早就有 hermes import-agent openclaw，還把 ClawHub 列成自己的 skill 來源 [S10][S11]：「匯入 OpenClaw 的 skill」已經有一個比 SYNOX 大很多的專案做得很好。推測 SYNOX 比較站得住的位置是「審查過的精選目錄＋權限範圍比較窄的執行端」，主打繁中、Telegram／Discord、個人和小團體、對 Windows 友善，不是比誰收的 skill 多。

建議路線（一句話版）

第 1 步（最小可行）

先接不含程式的純說明 skill（新增「只有說明」的 pack 種類，路線 A），加上 MCP 伺服器匯入（路線 C，用現成的 kind: mcp）。兩條都不會在這台電腦跑別人的程式。

第 2 步

synox import-skill 轉換器：把帶腳本的 skill 轉成 cli pack 草稿（路線 B），每個指令的危險程度由擁有者標，預設放進容器跑；Windows 個人版沒有沙盒，預設不准跑。

不建議（現在）

路線 D：做原生相容層、讓 SYNOX 給 AI 一個萬用 shell。這會打掉 SYNOX 最大的安全優勢，工作量也最大。

小工具：建議第一批

電腦效能監測、簡單 to-do、開發狀態紀錄（含目前在做哪個專案、分支規範檢查）、找檔案／定位資料夾。這四個用 SYNOX 現在的能力就做得出來。截圖要先補三樣能力（螢幕權限宣告、cli 回傳圖片、桌面工作階段），所以放第二批。完整清單在「小工具點子」頁。

這份沒有做的：沒下載任何 skill、沒 clone 任何專案、沒執行任何外部程式；外部資料都只透過網頁搜尋和讀網頁文字取得（2026-11-12）。ClawHub 現在到底有幾個 skill、裡面有多少能在 Windows 上用，都查不到可靠的數字，列在「下一步」當成要抽樣調查的工作。

怎麼讀這一頁

  • 接法：cli（指令進、文字出；AI 和網頁表單都能用）、排程（用 /schedule_add HH:MM /指令 每天跑，SYNOX 已經有）、webapp（本機網頁，計畫書工作包 W）、launch（只開桌面程式）、mcp（接現成的 MCP 伺服器）。
  • 權限對照 pack.json 的 capabilities：network（連網）、subprocess（開別的程式）、fs:own（只讀寫自己的資料夾）、fs:any（讀寫任何資料夾）。標 新 的是 SYNOX 現在還沒有的權限類別。
  • 敏感度：低／中／高（高＝可能碰到密碼、私訊、個人身分、財務）。
  • 優先序：P0 先做、P1 第二批、P2 有空再做、P3 先不做；工作量：S＜半天、M 約一天、L 好幾天（照 agent 的工作量估）。
  • SYNOX 現在：✅ 現在的能力就做得出來；⚠️ 做得出來但有限制；❌ 要先補能力。
  • 開源參考只寫名字讓之後查；未查證 授權和現況都沒有逐一確認，也沒有下載或執行過，參考時只讀它的文件。

原則

擁有者說「只要確保別人做的 skill 安全性夠，就可以 clone 下來吃進來」。查證後要先講清楚：沒有任何掃描能「確保」安全。VirusTotal 加 Code Insight 都還漏掉純文字指示和「行為型」攻擊 [S9][S24]，SYNOX 自己的文件也寫「掃描是提醒不是門」（docs/security.md）。能做到的是三件事：(1) 讓壞東西在裝之前被看見；(2) 讓它就算裝了也碰不到要緊的東西（沒有 shell、要宣告、容器、不能連網）；(3) 危險的動作一定要人按。SYNOX 原本的結構剛好在 (2)、(3) 很強。

S11更新時重審同名再匯入＝升級：除了現有的紅字項目，再加SKILL.md 文字差異（新增的網址、指令、安裝步驟用紅字）先上架乾淨版，之後再夾帶（Unit 42 提到的自動更新）部分有（packs/upgrade.py）；新（文字差異）
S12LLM 輔助審查（選用）擁有者按了才做：把 SKILL.md 和腳本交給 AI，請它列「跟宣稱用途不合的地方」；結果只是建議，不能讓裝不了的變成裝得了；送出前先顯示預估 token 量，只用擁有者設定的 AI 來源行為型攻擊（例如「一律推薦某個連結」）比較可能被讀出來新（預設關，因為要花錢）

對照 SYNOX 現在的五關

現有的關對匯入的 skill 夠不夠要補什麼
打包檔檢查（第 1 關之前）夠用：擋絕對路徑、..、符號連結、保留檔名、大小單行長度上限（S2）
第 1 關 宣告對 pack.json 夠；但外部 skill 沒有 pack.json，要由轉換器產生轉換器、kind: skill、platforms、source
第 2 關 靜態掃描只看 .py；完全不看 Markdown 的文字，而外部攻擊主要在文字裡文字層掃描（S3）、黑名單（S7）、環境變數和主機比對（S5）
第 3 關 完整性鎖定夠用：鎖每個檔案、每次載入都驗記錄來源（S1）
第 4 關 呼叫驗證夠用：擋參數夾帶、路徑跳出、把密鑰當參數送出—
第 5 關 授權與核准夠用而且是關鍵：DANGER 確認卡、結果包分隔符匯入的指令預設 DANGER、預設不給 AI（直到擁有者改）
沙盒／容器Linux 有（還沒在真機驗證）；Windows 沒有匯入的預設規則（S9）；長期是 AppContainer
「宣告」這件事兩邊的格式要的東西不一樣：Agent Skills 的 metadata 宣告「要哪些程式和環境變數」，SYNOX 的 pack.json 還要宣告「每個指令多危險、要什麼能力、資料屬於誰、能不能在群組用」。所以匯入時最花工夫的一步，是讓擁有者把這些補上。補完之後，SYNOX 就能照這些宣告出確認卡、限制權限。

跟其他平台的關係：三種選擇

選擇意思好處壞處建議
相容層（只吃別人的）能讀 SKILL.md 和 MCP，別人的東西轉進來用馬上有東西可以裝永遠在追別人的格式；品質和安全看別人—
自家標準只認 pack.json，別人要來就照 SYNOX 的寫法安全模型最一致沒人會為一個小平台另外寫一份—
雙向說明書用大家共通的 SKILL.md、接口用 MCP；SYNOX 自己只多一層 pack.json（安全宣告）；進得來，也出得去不另訂格式；SDK 寫的工具到處都能用；pack.json 成為賣點兩邊都要維護建議

來源授權能不能跟 SYNOX（AGPL 核心）一起散佈查證
ClawHub 的 skillMIT-0（一律）可以，連出處都不用標（建議還是標）已查證 [S1]

開發者流量：誠實評估

好的一面

格式已經統一（SKILL.md），接進來的成本確實低；MCP 讓一份工具能在很多平台用；SYNOX 有一層別人沒有的「指令級安全宣告＋確認卡」，在一連串 ClawHub 事件之後，「裝了比較放心」是講得出口的賣點。

不確定的地方

ClawHub 實際有多少 skill 能在 Windows、而且不需要 shell 的情況下用，沒有數字（推測不多）；一般使用者會不會在意「指令級宣告」，也還不知道。

風險

(1) Hermes 已經在吃 OpenClaw，規模大很多；(2) 外部 skill 出事，使用者會怪 SYNOX；(3) 外部格式一直變，維護會吃掉時間；(4) 每多一個 skill，每輪對話就多一點 token。

比較實際的期待：不是「把 OpenClaw 的流量吃下來」，而是 (a) SYNOX 的使用者不用重寫，就能用到一部分現成的 skill 和 MCP 伺服器；(b) 用 SYNOX SDK 寫的工具能拿到別的平台用，這才是吸引開發者的理由；(c) 「SYNOX 審查過」的精選清單成為一種品牌，量不必大，但每一個都可信。
