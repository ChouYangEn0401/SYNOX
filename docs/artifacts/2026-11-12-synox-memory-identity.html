記憶與身分檔：業界現在怎麼做，SYNOX 這一版做了什麼

研究＋功能交接。對象：擁有者（看「結論」「要你決定」兩頁就夠）與下一個接手的 session（其餘各頁）。 公開 repo 裡對應的是 docs/adr/0005-soul-ledger-memory-provenance-review.md；這一份是私人的，不進 SYNOX。

先講結論

  • 做了什麼：SYNOX 多了一本「soul 帳本」。常駐助理記進 soul.md 的每一條筆記，現在知道是誰加的、什麼時候、還對不對； 看起來像指令、有網址、或跟現有的很像的，不會自己寫進去，在主控面板等你按。
  • 為什麼先做這個：2024～2026 的公開事故與論文一致指出，「會被每一輪讀到、又是 AI 自己寫的記憶」是最容易被一句話污染的地方； 而評測顯示複雜的記憶系統（向量庫、知識圖）在這個資料量下不比「一份小而清楚的檔」好。所以這一版把力氣放在寫入的閘門、來歷、可以反悔，不是放在檢索。
  • 預設行為幾乎不變：沒有疑慮的偏好照舊直接記。差別只在有疑慮的那幾種會先問你。
  • 沒有新的相依套件、不連網、不開埠、不多叫 AI（整理是純字串比對，每 6 小時一次）。
  • 要你決定的有 5 題，都有建議的預設；不答＝照建議（見「要你決定」）。

外面怎麼做（2026-11-12 查）

怎麼讀這一頁：資料由兩個唯讀的研究子代理各自上網查、開過頁面後回報。Anthropic 的三頁文件是原文；其餘頁面是經過摘要模型讀的， 引用的數字要付印前請再抽查。標「未確認」的是沒有在開到的頁面上看到的說法。查詢字串都是通用主題，沒有帶任何個人或專案資訊。

1. 身分檔慣例：SOUL.md／USER.md／AGENTS.md／MEMORY.md（OpenClaw 一系）

  • 每段對話都載入：AGENTS.md（怎麼工作、怎麼用記憶）、SOUL.md（性格、語氣、界線）、IDENTITY.md、USER.md、有的話 MEMORY.md。
  • 上限由框架硬性執行：每檔 20,000 字、合計 60,000 字；USER.md 另有 4,000 字預算。超過只截「注入的那一份」，磁碟上的檔不動，並告訴模型被截了。
  • USER.md＝現在式的指示（Always／Never／Prefer），改了就取代舊的那行，歷史放每日筆記；MEMORY.md＝整理過的長期事實，只在私人主對話載入，群組不載。
  • 每日筆記 memory/YYYY-MM-DD.md 不每輪注入，要用時搜尋。壓縮脈絡之前有一輪安靜的「把該記的寫下來」。
  • 背景整理叫 dreaming（每天凌晨）：模型回的是「加／合併／取代」的決定，不是整份重寫；先快照，重寫如果掉了超過 25% 的舊條目就拒絕；有給人看的整理日記與「預覽不套用」模式。
  • SOUL.md 範本寫著「你改了這個檔要告訴使用者」。不受信任的 MEMORY.md／USER.md 不自動載入。
  • 2026 的變化：HEARTBEAT.md 不再是執行時讀的檔，心跳改成一般的自動化工作（預設 30 分鐘）。

2. AGENTS.md 標準與 Claude Code 的 CLAUDE.md、自動記憶

  • AGENTS.md：純 Markdown、沒有必填欄位；巢狀時「離被改的檔最近的那一份優先」，使用者當下說的話優先於一切。
  • CLAUDE.md：分層（組織、專案、本機、使用者），是串接不是覆蓋；建議每檔 200 行以內；可以 @路徑 匯入（最多四層）；HTML 註解在注入前會被拿掉。 文件明講：這些是「脈絡，不是強制設定」，要硬擋得用 hook 或權限設定。
  • 自動記憶：一份 MEMORY.md 索引（一行一件）＋每件一個主題檔；每次對話只載索引的前 200 行或 25KB，主題檔用到才讀；寫完會量大小、提醒合併過時的條目。

3. Anthropic 的記憶工具（Claude API）與官方對注入的說法

  • 記憶工具是用戶端執行的檔案操作（看、建、取代字串、插入、刪、改名），資料放哪由開發者決定（文件舉例可以是加密檔）。
  • 文件要求開發者自己做：路徑檢查（擋 ../）、寫入前濾敏感資料、檔案大小上限、很久沒讀的檔要過期。
  • 受管代理的記憶庫文件明講：預設可讀寫；代理如果處理不受信任的輸入，「成功的注入可以把惡意內容寫進記憶庫，之後的對話會把它當成可信的記憶讀回來」，參考資料請掛唯讀。每次變更留不可變的版本供稽核與還原。
  • 2026-05 的工程文章把「持久化的記憶污染」列為要處理的問題：注入一旦落在會被重新載入的地方，每次啟動都會回來。

4. Letta／MemGPT

  • 核心記憶＝幾個有標籤、說明、字數上限的區塊，永遠在脈絡裡；可以設唯讀。另外有可搜尋、不常駐的封存記憶。
  • sleep-time：背景另一個代理負責改核心記憶，主代理沒有改的工具。論文（數學題評測）說離線先想可以讓線上少花約 5 倍運算。
  • 2026 的變化：記憶改成一個代理自己擁有的 git 檔案樹（Markdown＋frontmatter，每次改都是一個 commit），背景整理改名 dreaming，預設沒有向量索引。

5. Mem0

  • 論文：兩階段——先從對話抽出事實，再對每個事實找最像的舊記憶，由 LLM 選 ADD／UPDATE／DELETE／NOOP。圖版本把過時的關係標成無效而不刪。
  • 2026 的變化（官方部落格與升級文件）：改成只加不改，一次 LLM 呼叫；理由是「覆寫有時抹掉關鍵資訊、刪除有時刪掉之後會用到的」。新舊並存，靠檢索排序讓新的浮上來。

6. Zep／Graphiti（時間知識圖）

  • 每個事實有四個時間：什麼時候成立、什麼時候失效、系統什麼時候知道、什麼時候作廢。新事實跟舊的矛盾時，把舊的「失效時間」設成新的「成立時間」——不刪。
  • 原始對話（episode）留著當來歷，事實與來源雙向索引。需要圖資料庫（Neo4j 等）。

7. LangMem

  • 三種記憶：語意（事實；可以是一份原地更新的 profile，或很多筆）、情節（成功的過往互動）、程序（代理該怎麼做，用改提示的方式存）。
  • 兩條寫入路：對話當下用工具寫（馬上生效但變慢），或回答之後在背景整理。

8. A-MEM 與 Generative Agents

  • A-MEM：卡片盒式的筆記（關鍵字、標籤、連結），新筆記會回頭改寫鄰居的描述——舊版本不留。
  • Generative Agents：取回的分數＝新舊（每小時 ×0.995）＋重要度（寫入時 LLM 給 1～10）＋相關度；累積的重要度超過門檻就做一次「反思」，寫出帶引用的心得。

9. 消費型產品的記憶設定（使用者看得到什麼）

  • Claude：記憶可以逐條看、改、刪；可以暫停、重設；無痕對話不進記憶；每個專案各自一份；有匯入匯出；敏感主題預設不存；刪掉對話不會刪掉從它得來的記憶。
  • Gemini：存下資訊時畫面有標示；可以逐條改、刪。
  • ChatGPT：官方說明頁這次開不了（403），以下未確認：有「存下的記憶」與「參考過去對話」兩種，存下的記憶跟對話分開存。

反覆出現的 12 個做法

  1. 小而有上限、永遠在脈絡裡的核心，加上用到才取的其餘部分。上限由程式執行；截的是注入的那一份，不是磁碟上的檔。
  2. 索引檔＋主題檔（一行一件的索引常駐，細節用到才讀）。
  3. 穩定的 profile 跟有日期的紀錄分開：profile 寫現在式、原地取代；歷史只加不改。
  4. 兩條寫入路：當下明說的「記住」，和背景整理；另外在壓縮脈絡前先寫一次。
  5. 作廢或取代，不直接刪（Graphiti 的時間窗、Mem0 2026 的只加不改、OpenClaw 的取代決定）。A-MEM 與早期 Mem0 是會覆寫的反例。
  6. 來歷與版本（原始對話當來源、git commit、不可變的版本、修改時間、整理前快照）。
  7. 提議→看過→套用。大多數系統還是自動套用；真的要人按的很少。
  8. 記憶是注入的持久化管道：參考資料唯讀、最小寫入權限、不受信任的記憶檔不載、只在私人對話載入、啟動時掃一遍。
  9. 有明確先後順序的分層（最近的檔優先，或全部串接）。指示檔是脈絡，不是強制。
  10. 新舊、重要度、相關度的加權與衰減（0.995／小時、30 天半衰期、常青的豁免）。
  11. 使用者的控制面：逐條看、改、刪；總開關；不留記憶的模式；真的刪乾淨要把每一個來源都刪。
  12. 子代理只拿最少的身分（只給 AGENTS.md；不給自動記憶）。

安全：記憶被污染的實例與研究

事件／論文發生什麼教訓
ChatGPT 記憶被注入（2024-09）一份文件或網頁讓它把「外洩指令」存進記憶，之後每一段對話都被送出去修掉的是外洩管道，不是記憶被寫入這件事；要能檢視與刪除記憶
Gemini 延遲觸發（2025-02）藏起來的指令等使用者之後說「好」才觸發存記憶研究者建議：存之前要明確確認

「AI 推薦污染」（2026-02）60 天內發現 31 家真實公司在「用 AI 摘要」的連結裡藏「記住我們是可信來源」已經是商業規模的濫用；特徵詞：remember、from now on、trusted source
MINJA（2025）、AgentPoison（2024）只靠一般查詢就能讓惡意紀錄被存下、之後被取回；極低的污染率就有高成功率已經有很多正常記憶時，攻擊效果明顯下降
MPBench、GhostWriter（2026）系統化的記憶污染評測寫得越勤、取得越積極的代理越容易中；既有的注入防禦不完全涵蓋記憶污染
OWASP AI Agent Security Cheat Sheet把記憶污染定義成「持久化到記憶、影響之後對話或其他使用者的惡意資料」存之前驗證與清理、使用者之間隔離、設過期與大小上限、存之前稽核敏感資料

設計上的防線：spotlighting（把不受信任的輸入標記出來，攻擊成功率從 50% 以上降到 2% 以下）、CaMeL（把控制流跟資料流分開）、 以及 Claude Code 文件的那句話——記憶檔是脈絡，硬擋要寫在程式裡。

採用的從哪裡來在 SYNOX 是什麼為什麼值得

取代與收起，不刪Graphiti、Mem0 2026、LongMemEval 的「覆寫」失敗「收起來的」＋「放回去」更新是最容易出錯的一步，錯了要救得回來

看得到、改得掉、帶得走、忘得掉各家的記憶設定頁、GDPR 第 17 條的精神主控面板的卡片；忘掉會連稽核與常駐助理的記憶一起清刪要刪到衍生出來的地方才算刪

沒採用的、為什麼

沒採用原因什麼時候該回頭看
向量庫、embedding、知識圖資料是幾十條、6000 字；評測顯示這個量全放就好。會多相依套件、多一份會漂移的索引要做「可搜尋的長期封存」（幾千筆）時
讓 AI 自動抽取每一輪對話的事實（Mem0 式）每輪多一次 AI 呼叫；寫得越勤越容易被污染擁有者覺得助理「學得太慢」時，而且只能產生提議
讓 AI 整理、合併、改寫筆記AI 改寫＝AI 自己產生下一輪的提示；A-MEM 式的改寫不留舊版筆記常常超過 20 條、字面規則抓不到的矛盾變多時；做成每天一次、只產生提議
自動覆蓋、自動過期刪除安靜地忘掉比多一條舊筆記更糟；Mem0 自己也退回只加不改不建議
對話助理的「記住這件事」工具會改 ADR 0001 的邊界（對話助理不寫 soul.md）——是擁有者的決定見「要你決定」第 2 題
把 soul.md 拆成 SOUL／USER／MEMORY 多個檔現在的四段已經是同一個意思（偏好、語氣、長期注意事項、助理筆記），量小不用拆筆記要超過 6000 字時，照「索引＋主題檔」拆
常駐助理的提示裡把 soul.md 包進每次隨機的分隔符會讓那段每次都變、吃不到提示快取；它沒有工具，寫入又已經有程式檢查常駐助理有工具的那一天
每日紀錄檔、壓縮前先寫記憶對話助理只留最近 6 輪、沒有壓縮這件事；對話封存是另一個功能做長對話時
成員各自的 soul.md 與帳本照 ADR 0002，這一版只有擁有者一份伺服器版要給成員個人化時（保管箱已經有每人一把金鑰）
啟動時用分類器掃記憶要多一個模型或多一次 AI 呼叫；現在用樣式比對擋在寫入那一步有便宜的本機分類器時

資料長什麼樣

soul.md 的字仍然只在 SoulStore（保管箱 runtime_soul）——你直接改的那一份才是正本。帳本只記「關於那些行的事」， 存同一個保管箱的 runtime_soul_ledger（加密）。帳本壞了或不見，筆記照舊在，只是沒有來歷。沒有事情發生之前不建這個檔。

{
  "v": 1,
  "notes":   { "<筆記代號>": { "added_at", "by", "source", "confirmed_at", "confirmations", "grounded"?, "approved"? } },
  "pending": [ { "id": "p-…", "kind": "add" | "retire", "text", "by", "source", "at",
                 "why": ["為什麼先問你", …], "related", "related_in_notes", "grounded"?, "told",
                 "nid"?, "reason"?, "pair"? } ],
  "archive": [ { "id": "a-…", "text", "added_at", "by", "source", "retired_at", "reason", "replaced_by" } ],
  "suppress": [ "<雜湊>", … ],          // 你拒絕、收起、要它忘掉的；只有雜湊，沒有字
  "day": "2026-11-12", "auto_today": 2,   // 每日自動寫入的計數
  "told_day": "2026-11-12"                // 今天通知過了沒
}
  • 筆記代號＝那一行去掉開頭的 -、空白、標點並轉小寫之後的 SHA-256 前 12 碼。你改了字＝另一條，原本的來歷不跟過去（畫面顯示「你寫的或以前就有的」）。
  • 上限（ledger.py 最上面的常數）：筆記 40 條、每天自動 6 條、提議 20 則、提議 30 天過期、收起來的 200 條、90 天沒確認算舊、挑選時 30 天半衰期。

流程

常駐助理想記一條（心跳的 SOUL+:）

常駐助理回 "SOUL+: 一行"
   │  heartbeat._soul_lines → SoulLedger.propose(lines, by="mother", source="heartbeat", evidence=你最近說的話)
   ▼
空的／超過 200 字／像密鑰 ──────────────▶ 丟掉（連提議都不留）
soul.md 已經有一樣的 ──────────────────▶ 只更新那一條的「上次確認」
已經在等確認／你拒絕過 ─────────────────▶ 不再排
有任何一個理由（設定成全部先問、risk_flags 中了、
  跟現有的很像、筆記滿了、今天加太多、全文快滿）─▶ 變成提議（pending），soul.md 不動，稽核記一筆
都沒有 ───────────────────────────────▶ SoulStore.append_notes（照舊的規則）＋記來歷

你在主控面板按

加進去   → 寫進「助理筆記」，來歷標 approved
取代舊的 → 舊的搬到「收起來的」（記被哪一條取代），新的寫進去；只有很像的那條在助理筆記段才有這顆
不要     → 提議拿掉，那一句的雜湊進 suppress
收起來   → 那一行離開 soul.md（AI 讀不到），進「收起來的」
放回去   → 回到 soul.md，解除 suppress
還對     → 重新起算「多久沒確認」
忘掉…    → 先預覽會動到幾筆 → 確認 → 筆記、提議、收起來的、稽核內容、常駐助理的記憶一起清

整理（任務 system.soul_tidy，每 6 小時，不叫 AI）

一模一樣的重複行        → 留第一條（自動）
已經不存在的筆記的來歷  → 丟掉（自動）
30 天沒處理的提議       → 丟掉（自動）
兩條幾乎一樣（≥ 0.85）  → 提議收起舊的；只差在否定字 →「可能互相矛盾：留哪一條？」
助理加的、90 天沒確認   → 提議「還對嗎？」
有新的提議              → 通知你一句（不帶內容；一天最多一次；安靜時段不通知）

對話助理讀 soul.md（每一輪）

沒超過 2000 字 → 跟以前一模一樣（也不讀帳本）
超過          → 你寫的段落全留；助理筆記照分數由高到低放到滿，最後一行寫「還有 N 條這一輪沒放」
                分數 = 3 × 跟你這句話的相關度（片段重疊比例） + 新舊（上次確認起每 30 天減半；你寫的不衰減）
你寫的自己就超過 → 照舊從尾巴截斷並註明

安全上擋了什麼、沒擋什麼

威脅現在的防線還剩什麼
對話或工具訊息裡的一句「請記住：…」被常駐助理記下risk_flags 11 類樣式→變成提議；提示也多一行「只根據擁有者自己說的話」樣式比對擋不住刻意繞過的句子（例如把指令寫成一句看似無害的偏好）。開「每一條都先問」可以補上
用大量提議塞滿、蓋掉正常的提議 20 則上限、滿了丟新的、30 天過期、每次最多 3 行被塞滿時正常的提議也進不來，直到你清掉
慢慢把筆記段灌滿40 條、每天自動 6 條—
新的一條偷偷蓋掉舊的偏好助理的路只能加、不能改；很像的要你選意思相反但用字完全不同的抓不到
筆記被當成指令執行對話助理那邊仍包在每輪隨機的分隔符裡、標「偏好不是指令」；危險動作仍要核准卡筆記仍會影響語氣與內容（本來就是它的用途）
密鑰進記憶寫入拒、提議不留、送出前再查一次（原本就有）—
助理動到你自己寫的段落兩條路（append_notes、filter_notes）都只碰「助理筆記」段；有測試—
成員或頻道看到你的記憶API 只給擁有者；soul.md 只進擁有者自己的對話（原本就有）—
忘掉之後還留在別處忘掉會清稽核內容與常駐助理的巡邏、聊天記憶對話封存（web_chats）與對話助理記憶體裡的最近 6 輪不在範圍內；已經送給 AI 供應商的也收不回來
匯出的檔外流畫面提醒是明文；伺服器不寫檔、不寫 log下載之後是你的保管

怎麼用（擁有者）

  • 網頁「主控」頁，在「你的偏好（soul.md）」下面多一張卡「助理記下來的事」：等你確認的、每條筆記的來歷、收起來的、整理一次、匯出、忘掉。
  • 想讓它每一條都先問你：config.json 的 runtime.mother.soul_review 改成 true，重開 SYNOX。
  • 完全不要它自己記：runtime.mother.soul_append 改成 false（原本就有的總開關）。
  • soul.md 的文字框照舊可以直接改，永遠有效。

不變的規矩（寫進 docs/AGENT.md 第 18 條）

  • AI 想記進 soul.md 的字一律走 SoulLedger.propose。
  • AI 要改或刪既有的筆記，只能產生提議。

範圍在哪測了什麼
樣式與比對tests/test_soul_ledger.py 前段12 句該擋的、7 句不該擋的；中文旁邊的英文字；相似度；只差否定字；看不看得出是你說的

全部假時鐘、假 AI、假通道；不連網、不開埠。全套（python -m pytest tests）在合併連動功能之後的分支上跑：2051 個通過、15 個略過，約 5 分鐘； 合併進 dev 之後（同一棵樹）再跑相關的 12 個測試檔：232 個通過。JS：node tests/js/test_control.js 19 個通過。

還沒驗證的（接手的人請先做這幾件）

#還沒驗證怎麼驗風險
1主控面板的新卡片沒有在真的瀏覽器上按過（只測了純函式，靜態預覽有重產）雙擊 docs/ui/preview.html 切到主控頁看排版；再開真的 SYNOX 按一輪中 排版或事件接線可能有錯
2「匯出（下載）」用瀏覽器的 Blob 下載，在這一頁的內容安全政策下沒實測真的按一次；不行的話改成伺服器回 Content-Disposition中
3真的 AI 會不會照新的提示行（只根據擁有者說的話記）用真的 AI 跑幾次心跳，看 SOUL+ 的內容低 程式檢查不靠它
4risk_flags 在真實筆記上的誤擋率、相似度門檻（0.6／0.85）在真實中文筆記上的表現用兩週；看「等你確認」裡有多少其實是正常的低 誤擋只是多按一下
5你直接存 soul.md 與帳本操作同時發生（兩把不同的鎖）理論上的競爭；單一使用者幾乎不會遇到低
6真的保管箱（DPAPI）下每次存檔的時間：一次提議最多存 3～4 個檔，每個都要重新衍生金鑰計時一次心跳低
7沒有跑任何公開的記憶評測（LongMemEval 之類）不建議跑：公開評測測的是長對話問答，不是這裡做的事。建議改成自己的 10 題小回歸（更新、時間、該拒答）—
8研究頁裡 2026 年的幾個說法（OpenClaw 取消 HEARTBEAT.md、Mem0 改成只加不改、Letta 改成 git 檔案樹）與 2026 年的 arXiv 編號，是子代理讀頁面後回報的，我沒有逐一複查引用到對外文件前，照「來源」頁的網址再開一次低 不影響程式

要你決定的（不答＝照建議）

1. 常駐助理想記的事，要不要「每一條」都先問你？

這題接的是 SYNOX 的 Q6（還沒回答的那題）。這一版沒有替你回答，只是把原本的「全部直接記」改安全了一點。

選項一句話
A. 照現在這一版：沒疑慮的直接記，有疑慮的先問平常不用按；奇怪的那幾種進不去建議（預設）
B. 每一條都先問（soul_review: true）最安全，研究上最被推薦；但每一條都要你按
C. 完全不讓它自己記（soul_append: false）soul.md 只有你自己改

建議 A 用兩週，看「等你確認」與筆記的品質；出現過一次你覺得不該自己進去的筆記就改 B。

2. 你在聊天裡說「記住這件事」時，對話助理可以把它送成提議嗎？

現在對話助理不能寫 soul.md（ADR 0001 的邊界）。你親口說的是最可信的來源，各家都有這條路。

選項一句話
A. 可以，但只能送成提議（你在主控面板或卡片上按了才進去）說一句就好，不用自己去改文字框；仍然過同一套檢查建議（下一版做）
B. 可以，而且你明說的直接寫進去最順；但「你說的」跟「貼進來的內容裡寫的」AI 不一定分得清
C. 不要，維持現在要記的事自己到主控面板打

3. 有新的提議時要不要通知你？

選項一句話
A. 照現在：一天最多一句、不帶內容、安靜時段不通知不會漏、也不吵建議（預設）
B. 不通知，自己到主控面板看最安靜；可能放到過期（30 天）
C. 直接在 Telegram／Discord 送卡片讓你按最方便；要另外做（半天左右）

4. 要不要讓 AI 幫忙整理筆記（合併、找矛盾）？

選項一句話
A. 先不要：現在用字面規則，不多花 AI 的錢筆記還少，規則夠用建議（預設）
B. 每天一次讓 AI 看一遍，但它只能提議、不能自己改抓得到用字不同的矛盾；一天多一次 AI 呼叫

5. 公開 repo 裡的 ADR 0001～0003、兩份交接單與待決題檔，有逐字引用你說的話的段落，和私人專案的名字

這次寫 ADR 0005 時看到的（不是這次造成的；這次的 ADR 沒有這些）。它們已經在公開的 dev 上。這次沒有動。工作單：_inbox/20261112-233952-public-adr-verbatim-quotes.md。

選項一句話
A. 把那幾段改寫成轉述、專案名換成通稱（之後的版本不再出現；歷史紀錄裡還在）花十幾分鐘；最划算建議
B. 維持現狀你覺得那些話可以公開就不用動
C. 連歷史一起清（改寫 git 歷史）要強制推送，會影響所有拉過的人；這台電腦的規矩是不強推
