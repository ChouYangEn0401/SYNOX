結論

  1. 可以架，但要先分清楚程式在誰的機器上跑。工具在作者自己的伺服器跑、SYNOX 只是去呼叫它，這條路現在就能開放，風險最低。工具的程式要在你的機器上跑，在這台 Windows 10 家用版上目前沒有任何真的隔離，不該對不認識的作者開放。
  2. 檢查別人的危險程式碼，做得到篩選，做不到保證。靜態掃描和 AI 審查都只能抓到明顯的和已知的。有心藏的人藏得過。VS Code、Claude Code 的外掛也是同樣的極限。
  3. 真正讓它變安全的是三件事。隔離（它碰不到）、最小權限（它拿不到）、可撤銷（出事能馬上停、查得到）。檢查只是第一道篩子。
  4. SYNOX 的底子已經比多數同類專案好。安裝五關、檔案鎖、信任層級、角色上限、確認卡都有。缺六塊：隔離沒在真機驗過、沒有簽章、沒有網路出口白名單、第三方寫的字會進 AI 的系統提示、工具面板跟網頁同源、沒有每個工具的呼叫紀錄與一鍵停用。
  5. 建議選 A。現在只開放不在你機器上跑的工具，同時補便宜的缺口。等另一台 Linux 機器把隔離驗過，再升到 B。

威脅：別人的工具可能做什麼

排序看三件事：多容易發生、損害多大、SYNOX 現在擋不擋得住。

讀憑證、把資料送出去P0

Python 工具讀保管箱解開的東西和設定檔裡明文的 bot token。命令列工具讀整台電腦。有連網權限的工具把東西送到自己的伺服器。個人版與 Windows 擋不住。

跨使用者讀資料（伺服器版）P0

一個成員用的工具讀到別的成員的筆記、記帳、token。程序內的工具擋不住；子程序要等真隔離。

供應鏈P1

第一版乾淨、第二版加料。相依套件裡藏惡意程式。每次從網路抓最新版來跑。升級紅字與檔案鎖擋事後偷改，但套件內容不看。

騙 AI（提示注入）P1

工具簡介、技能說明、工具回傳的結果、遠端伺服器回的字裡寫指令。遠端伺服器可以今天正常、明天改行為。工具結果有包標記加確認卡；簡介類的字沒包。

借使用者的身分操作網頁P1

惡意面板用開啟者的登入狀態打網頁的後台。目前沒擋。

提權與留後門P1

改鎖檔、改別的工具、寫開機啟動項。沒有隔離就擋不住。

資源耗盡P2

吃光記憶體、開一堆程序、卡住 SYNOX、燒光 AI 額度。命令列有 120 秒逾時，AI 有額度。Windows 預設不限記憶體。

冒名與搶名P2

取跟官方工具一樣的名字、寫別人的發行者名字。同名會走升級流程出紅字；發行者沒簽章。

你作為營運者的責任P3

別人的資料在你機器上被第三方工具弄丟或外洩。這不是程式問題：要告知、要能撤銷、要有紀錄。

這台電腦的特別之處

它是你的開發機，不是乾淨的伺服器。上面有所有專案的原始碼、多個登入中的 session、瀏覽器裡的帳號，記憶體只有 12 GB。一個沒隔離的第三方工具在這台出事，損害範圍不只是 SYNOX 的資料。這是選項 A 堅持陌生人的程式不在這台跑的主要理由。

沙箱的幾種做法，放在這台電腦上看

條件：Windows 10 家用版、12 GB 記憶體、不開網路埠、不跑重負載。

做法隔離強度這台能用嗎判斷
子程序加資源上限弱：檔案和網路都不限能，已實作只防吃光記憶體，不能當安全邊界
Windows AppContainer中理論上能；Python 在裡面跑不跑得起來沒人驗過工程量與不確定性最高，先不押
容器（Docker Desktop）中高裝得起來，但常駐吃 GB 級記憶體這台不裝，放到另一台 Linux
Linux 的 bwrap 或 podman中高不能，要 Linux選項 B 的主力；程式已寫好，差真機驗證
WebAssembly 沙箱高：預設沒有檔案、沒有網路能，不用虛擬化、不開埠最適合這台的長期方案，但工具要改寫，放在選項 C
整台虛擬機最高太重這台不做
程式不在你這裡跑對你的機器而言最高能，已實作選項 A 的核心

出口白名單可以不開埠：工具完全斷網，要抓網頁時經標準輸入輸出向 SYNOX 提出請求，SYNOX 核對宣告的主機後代抓。這跟現在命令列工具的資料來回是同一種管道（設計構想，還沒實作）。

檢查別人的程式，到底多可靠

靜態分析

做得到
  • 抓出用了卻沒宣告的能力
  • 抓出常見的危險寫法與常見的繞法
  • 比對相依套件的已知漏洞（只對已經登記的有效）
  • 抓到不小心留在包裡的密鑰
  • 列出所有看不懂的檔
做不到
  • 判斷任意程式會不會做壞事。這在理論上已證明不可判定
  • 看穿 Python 的動態寫法。SYNOX 自己的兩輪審查就找到二十多種一行繞過
  • 看到相依套件內部、執行檔、遠端伺服器
  • 分辨合法權限的濫用：天氣工具順便把你的查詢送給別人，程式碼跟正常功能一樣
  • 抓到延遲或條件觸發

Python 核心開發者花三年做 Python 內的沙箱，2013 年公開宣布這個做法「broken by design」，結論是要把整個 Python 程序放進外部沙箱（來源 S9）。

AI 審查

做得到
  • 用白話說明這份程式看起來在做什麼，對照說明文件找出不一致
  • 抓到相當比例的常見漏洞類型。2026 年一份研究中商用模型偵測率 89 到 96%（S11）
  • 刻意寫來騙 AI 的註解，在那份研究裡影響很小
盲點
  • 貼近真實的資料上差很多。2024 年的研究：同一個模型在舊評測 68%，在較真實的資料只有 3%（S10）
  • 檔案一大就漏（S12，次級來源）
  • 每次結果可能不同
  • 看不到執行期、相依套件、遠端行為
  • 最危險的是心理效果：「AI 看過了」容易被當成「安全」
建議寫進設計的規則

AI 審查的結果只能增加紅字，不能消掉其他檢查的紅字，也不能自動核准。它是給審核的人看的摘要。

一句話：檢查能把粗心的作者和懶惰的攻擊者擋在門外，擋不住認真的攻擊者。設計上要假設檢查會漏，讓漏進來的東西碰不到重要的資料。

Claude Code 外掛信任加警告，不隔離

「A Claude Code plugin you install can execute arbitrary code on your machine with your user privileges.」安裝前顯示信任警告：Anthropic 不控制外掛內容，也無法驗證。沙箱只包 shell 指令，外掛的 hook 與 MCP 伺服器在沙箱外。原生 Windows 沒有沙箱。社群目錄會釘住版本，組織可以設允許與封鎖清單。

S1、S2、S3

MCP 規格的安全建議要求同意，建議沙箱

本機 MCP 伺服器就是下載到使用者機器上執行的程式。一鍵設定前必須完整顯示要執行的指令並取得同意；應該放進沙箱並限制檔案與網路。另有「工具投毒」：惡意指令藏在工具說明裡，人看不到、AI 看得到；伺服器可以在你核准之後才改說明。

S4、S5

VS Code 擴充上架檢查加撤銷，不隔離

擴充主機「has the same permissions as VS Code itself」。上架時有惡意軟體掃描、簽章、發行者驗證、密鑰掃描；確認惡意後列入封鎖清單並自動解除安裝；第一次裝第三方發行者要按信任。即使如此，仍有惡意擴充上架後才被研究者發現（次級來源）。

S6、S13

Deno預設零權限

預設沒有任何檔案、網路、環境變數、子程序權限，用旗標逐項開。但開了子程序或原生函式庫就「equivalent to --allow-all」；同一個程式裡的相依套件權限相同，無法只限制某一個。跑不可信程式時官方建議再加一層系統沙箱或虛擬機。

S7

WebAssembly（WASI）能力制沙箱

沒有系統呼叫，一切靠主程式給；檔案只碰得到被交付的。Spectre 類攻擊的緩解仍在研究中。資源上限的文件這次沒查到（未驗證）。

S8、S14

Cloudflare Workers多層隔離加全職團隊

每個租戶一個 V8 isolate，整個程序再包一層沙箱（空的檔案系統、禁止網路），V8 修補 24 小時內上線。平台方可以攔下客戶程式的對外請求做允許、封鎖、記錄。官方自己說這是「an ongoing investment — not something that will ever be done」。

S15、S16

對照之後的四個結論

  1. 沒有任何一家只靠掃描。
  2. 桌面端的外掛生態本質上是信任、警告、可撤銷，不是隔離。SYNOX 現在跟它們同一級，而且安裝前列得更細。
  3. 真的讓陌生人的程式給陌生人用的平台，是多層隔離加全職安全團隊。
  4. 小專案最划算的模式：程式在別人那裡跑，你只跟它交換有格式的資料、給它範圍很小的憑證。SYNOX 已經有這條路。

建議路線

階段 0　現在就能定的規矩

不寫程式
  • 不認識的作者：只收遠端工具。
  • 有程式碼的工具：只收認識的人，信任一律選第三方。
  • 不做：不在這台開發機裝陌生人含程式的工具；不對外說工具都檢查過所以安全。

驗收：安全文件「情境三」的建議與這裡一致（現在已經一致）。

階段 1　最小可行（選項 A）

這台可測，不跑第三方程式
  1. 第三方的字不進系統提示的信任區。限長度、去換行，放進資料標記。驗收：簡介寫「忽略規則」的假工具，字出現在標記內；有換行的被拒裝。
  2. 面板隔離。第三方工具的面板拿掉同源權限，或乾脆不給面板。驗收：面板腳本讀不到外層頁面。
  3. 呼叫紀錄、一鍵停用、封鎖清單。記誰、何時、哪個指令、成功與否，不記內容。驗收：停用後下一次呼叫就被拒，不用重開。
  4. 簽章。工具庫目錄與每個工具檔簽名；發行者名字綁公鑰；換金鑰出紅字。驗收：改一個位元組就拒裝。
  5. 相依套件檢查。第三方工具的套件一律要寫雜湊；報告加已知漏洞欄（預設關，你明確開才連網查，只送套件名與版本）。
  6. 個人版也補掃。手動放進來、沒有鎖的工具，載入前也掃。
  7. AI 審查摘要（選配）。只能加紅字。驗收：關掉時流程完全不變。

不做：不裝容器、不開放陌生人含程式的工具、不做線上目錄。

階段 2　關在容器裡跑（選項 B）

需要另一台 Linux
  1. 真機驗證。照現有的驗證清單把容器與 Linux 沙盒真的跑一遍。驗收：斷網真的斷、讀不到別人的資料夾、資源上限生效，逐項有紀錄。
  2. 第三方只准子程序型。不收第三方的 Python 程序內工具。
  3. 出口白名單。工具斷網，經 SYNOX 代抓宣告的主機。驗收：連沒宣告的主機被拒且留紀錄。
  4. 審核佇列。上傳、自動檢查、等核准、上架；更新走同一條。驗收：沒核准的版本任何成員都叫不到。

不做：不在這台開發機跑容器。

階段 3　完整平台（選項 C）

等真的有外部作者再評估

公開目錄與作者帳號、金鑰輪換與撤銷清單、給純運算工具用的 WebAssembly 沙箱、給高風險工具用的虛擬機、漏洞回報與下架流程、給使用者的資料處理說明。每一項都需要持續的人力。

哪些情況下不該架別人的工具

  1. 工具的程式要在這台開發機上跑，而作者不是你認識、找得到的人。
  2. 工具是 Python 程序內型，而你不是完全信任作者。個人版、伺服器版都一樣。
  3. 工具附執行檔、或每次從網路抓程式來跑，而那台機器沒有驗過的隔離。
  4. 伺服器上已經有別人的私人資料，而隔離還沒在那台機器上真的驗過。
  5. 工具同時要連網和讀使用者資料，而你沒有出口白名單。
  6. 工具處理金流、醫療、帳號密碼這類出事代價很高的資料。
  7. 作者不願意給原始碼、不願意釘死版本與雜湊。
  8. 你沒有時間持續審更新、處理回報、在出事時下架。上架是持續的責任。
