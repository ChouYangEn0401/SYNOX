CC Open 實作調查

2026-11-13 · 調查對象 MyFirstTelegramClawBot（唯讀，沒有執行任何程式）· 目的：在 SYNOX_Libs 寫類似的小工具

結論

  1. CC Open 就是 /proj_edit（舊名 /cc_open）。Bot 自己不跑 AI，只在白名單專案的資料夾裡開一支固定的 claude remote-control --name "TG·專案" --permission-mode default。之後在手機 Claude App 或 claude.ai/code 接手，每一步自己核准。
  2. 啟動方式是 Python subprocess.Popen：argv 陣列、不經 shell、不開視窗，輸出寫進 log。stdin 餵 y\n 答掉「Enable Remote Control?」，再從 log 用正規表示式撈出第一個 https://claude.ai/… 連結。
  3. 能活過 bot 重啟：Windows 上每支放進自己的 Job Object 並脫離 bot 的 Job；pid＋行程建立時間存檔，重開後認回。預設 35 小時到期，可加時。
  4. 最大的坑是「資料夾信任」：第一次在某資料夾跑時，claude 要人按一次信任，背景模式答不了。
  5. 要搬的核心很小，而且 SYNOX 已內附同一套行程管理（vendor/isdtelekit/jobs/runner.py），不用再抄。Telegram 狀態卡、按鈕、白名單、審查都要拆掉。

一次「開」的流程

/proj_edit X
 → 權限：擁有者？私訊？/sudo 解鎖中？
 → 只在白名單專案裡找 X；沒過安全審查就擋下
 → 已經開著？回現有連結。已達 8 個上限？拒絕
 → 找 claude 執行檔、拿掉 5 個環境變數、組 argv
 → JobRunner 啟動（背景、stdin 餵 y）、寫 cc_sessions.json
 → 每秒讀 log，最多 20 秒，撈 claude.ai 連結
 → 撈到：訊息改成「開好了＋連結」
 → 很快就死且 log 有 trust：給「信任資料夾」按鈕

主要檔案都在 src/clawbot/：commands/cc_commands.py、claudecode/launcher.py、core/jobs.py。

實際用到的指令

情境argv
一般開claude remote-control --name "TG·專案" --permission-mode default
接回某段對話同上，再加 --session-id=<id>（寫成一個 token）
  • 沒有用 -p、stream-json、--resume、tmux。--resume 與 --cloud 在專案裡被記為死路。
  • 權限模式只准 default／acceptEdits／plan／auto，bypassPermissions 會退回 default。
  • 工作目錄來自掃描結果，不收 Telegram 傳來的任何路徑。
  • 環境變數拿掉 5 個：ANTHROPIC_API_KEY、ANTHROPIC_AUTH_TOKEN、Bedrock、Vertex、CLAWBOT_SERVICE。其餘全部照傳。
  • 不要跑 claude remote-control --help：它不印說明，會直接開一個伺服器卡住。

兩道每次都會遇到的提示

提示背景模式答得了嗎做法
Enable Remote Control? (y/n)答得了stdin 餵 y\n
信任這個資料夾嗎（每個資料夾第一次）答不了沒信任就印 Workspace not trusted 並在約 0.6 秒內退出。另有三條補救路，見下
  • /proj_trust：開一個真的主控台視窗讓人按。
  • 改 ~/.claude.json：2026-10-02 試過無效，後來換寫法加回來，真機上有沒有效沒驗證。
  • ConPTY 偽終端機替人按（需要 pywinpty）：等於繞過 claude 的一道安全提示。
  • 已信任 repo 的 git worktree 不用再信任（只在 claude 2.1.291 驗過）。

狀態管理

事情做法
防止重複一個專案最多一個伺服器，同時最多 8 個。要平行就開 git worktree（lane）
期限預設 35 小時；到期前 15 分鐘提醒；加時累加在原期限上
重啟認回啟動時讀 cc_sessions.json，用 pid＋行程建立時間認回（防 pid 被重用）
關閉自己開的用 TerminateJobObject；認回來的只能 taskkill /T /F
結束紀錄寫入 cc_ended.json（最近 40 筆）；停掉後 4 小時內可接回的對話記在 cc_revivable.json

權限與風險

  • 誰能開：只限機器擁有者、只在私訊、要先用手機驗證器 /sudo 解鎖。lane=new 和 resume= 要當場再驗一組碼。
  • 能開哪些專案：要過四關：白名單、安全審查 SAFE、資料夾被信任過、不在封鎖清單。
  • 風險 伺服器開著的 35 小時內，誰拿到你的 claude.ai 帳號，就能遙控這台電腦。
  • 風險 環境變數只拿掉 5 個，其他變數（可能含密鑰）都傳給 claude。
  • 風險 改 ~/.claude.json 會動到所有 claude 共用的設定檔。

搬到 SYNOX_Libs：能搬與要拆

能搬（核心）要拆掉（Telegram／ClawBot 專屬）
組 argv、權限模式白名單、拿掉環境變數清單、撈連結與 session id（純函式）、啟動監看、結束分類、狀態檔與重啟認回、期限與加時 Telegram 狀態卡與按鈕、白名單與安全審查、/sudo 驗證、lane、ClaudeLogin 相依（改用 SYNOX 的 find_claude()）

設計重點：工具不決定誰能開、能開哪個資料夾，只收呼叫端已經允許的資料夾。結果用「事件」丟給呼叫端，由前端決定怎麼顯示。完整的類別與函式簽名草案在報告第 7.3 節。

建議選項

選項內容
A只做核心：純函式＋啟動器（用 SYNOX 內附的 JobRunner）。遇到沒信任只回事件，請人自己到電腦前跑一次 claude建議
BA 再加「開主控台視窗讓人按信任」。服務模式不能用之後再說
C照搬全套，含改設定檔與偽終端機不建議

驗收（A）：用假的 claude（印出假連結的 Python 腳本）測過「開→撈連結→加時→到期→結束事件→重啟認回→接回」。不在這台電腦開真的伺服器。

未驗證的事項

  • taskkill /F 收掉伺服器後，官方說的「4 小時內可接回」是否照樣成立。
  • claude remote-control 是否只對外連線、不在本機開埠。這台電腦規定不開網路埠，動手前要先查官方文件。
  • 寫成 SYNOX pack 時，哪種形式過得了 policy 的權限與沙盒，沙盒裡 claude 還連不連得到 claude.ai。報告只讀了這幾個檔案的片段。
  • SYNOX 的 find_claude() 不採用 VS Code 擴充裡的 claude，跟 ClawBot 找到的可能不是同一版。
  • 非 Windows 上認回時沒有比對行程建立時間，有 pid 被重用的風險。
  • log 裡對話標題的格式（OSC 8 超連結）可能隨 claude 版本改變。
