🧪 定位：實驗品，不算核心。擁有者 2026-11-12 的方向是 SYNOX 核心維持空殼、指令盡量少，所以 link 之後很可能整包搬成獨立套件（或 pack），也可能拿掉。config 沒開 link 時它完全不存在（沒有指令、沒有執行緒、沒有檔案）；核心只在 app.py、config.py、doctor.py、__main__.py 各 import 一處，搬出去時要接回的切面列在 docs/link.md「要搬出去時」。

做了什麼

調查文件第 04 節那五層全部有程式；傳輸層做了 memory（測試）、folder（共用資料夾）、tcp（區網）三種。設計上的重點是安全跟路分開：信封端對端加密＋簽章，傳輸層只搬 bytes，所以之後加 MQTT 或序列埠不用碰安全層。

怎麼在兩台真機上試

兩台 Windows（或一台 Windows 一台樹莓派）在同一個區網。下面的 192.168.1.10 換成主控台的 IP。

  1. 兩台都切到這個分支、裝好（Setup.bat 或 pip install -e .[dev]），各自的 bot 原本就能跑。
  2. 主控台 config.json 加：
    "link": {"enabled": true, "role": "console", "name": "主控台",
         "transport": {"kind": "tcp", "listen": "0.0.0.0:8831"}}
    哨兵加：
    "link": {"enabled": true, "role": "worker", "name": "客廳",
         "transport": {"kind": "tcp", "connect": "192.168.1.10:8831"}}
    （Windows 防火牆會問主控台的 8831；只允許私人網路。）
  3. 兩台 python -m synox doctor --offline：應該各有一行 link：開，主控台／哨兵…。
  4. 兩台都 Start.bat（或 python -m synox run）。哨兵視窗應出現 [LINK] connected to 192.168.1.10:8831。
  5. 主控台電腦：python -m synox link pair → 複製那一行 SYNOX-PAIR-1:…。
    哨兵電腦：python -m synox link join "<那一行>"。15 秒內主控台視窗出現 [LINK] paired worker …。
  6. 主控台的 Telegram：/link_status（哨兵應該 🟢）→ /link_run 客廳 /note 買牛奶 → 幾秒後收到「✅ 任務 … 完成」。哨兵的 Telegram /note_list 看得到那筆。
  7. 再試：/link_run 客廳 /note_clear（應被拒：danger 超過 max_effect）、/link_redo、/link_cancel、把哨兵關掉再開（應自動重連、/link_status 先 ⚪ 後 🟢）。
  8. 開不了埠的話改走資料夾：兩台都寫 "transport": {"kind": "folder", "dir": "\\\\NAS\\synox-link"}、"heartbeat": 0；其餘步驟一樣（配對請求也走資料夾，慢幾秒）。

測試現況

  • 新的 18 個（tests/test_link.py）：名片與身分、信封竄改／改收件者／改 seq／陌生寄件者／重放／時鐘、配對只在允許時看名片、設定解析、事件匯流排、資料夾傳輸、TCP 框架（socketpair）與沒驗過三次就斷、三台 SYNOX 的派任務→真的做了→通知、拒 danger／未知指令／陌生機器／非主控台的任務、重做與交接的 lineage／context、離線送不出去、取消、心跳在線，以及 CLI（card／pair／join／trust／forget）與 doctor。全部不綁埠。
  • 整套：1439 過、1 略過、12 失敗。那 12 個在改動前就失敗，原因與 link 無關：5 個 test_llm 要 ntu_easy_llm（開發機沒裝）；7 個是環境的事：Windows 路徑或登錄檔的預期值（C:\…、Software\Classes、PowerShell）、或這台容器沒有 systemd（sandbox 後端的測試），在 Linux 開發機本來就過不了。
  • 手動：真的 TCP listen／connect 在 127.0.0.1 跑過一次：配對、ping／pong、主控台重開後哨兵退避重連都正常。沒在 Windows、沒跨機器。

真機驗證清單（給拿到兩台的人）

  • Windows 防火牆對 8831 的提示；只允許私人網路後哨兵連得上
  • 兩台時鐘差 > 5 分鐘時信封被拒（log 寫「時間差太大」），對時後恢復
  • 哨兵關機 → 主控台 /link_status 在 ~90 秒內變 ⚪；開機後自動 🟢
  • 主控台重開：哨兵在 1→2→4…60 秒退避內重連；seq 不倒退（沒有「seq 不比上一封新」的拒信）
  • 派一個會跑 30 秒以上的 cli pack 指令：結果回得來、task_timeout 的行為
  • 派一個會出圖片的指令：主控台現在只看到 [圖片 路徑] 一行（已知限制）
  • 資料夾傳輸走 NAS 分享：Windows 的 SMB 鎖檔不會讓 .msg 讀不到（讀不到會下一輪再試）
  • 樹莓派當哨兵：Python 3.11+、cryptography wheel 裝得上、sandbox 後端 bwrap／systemd-run
  • scripts/prepublish_check.py 在真機 data/ 不在 git 的前提下仍然零發現

還沒做的

項目現況要做的話
跨網段兩台要同一個區網、WireGuard，或共用資料夾先用 WireGuard（不用改程式）；之後可寫 relay 傳輸（兩台都主動連一台只搬密文的小 VPS）
MQTT／序列埠傳輸介面留著（六個方法），沒有實作各約 150 行；MQTT 要 paho-mqtt 與一台 broker
任務中途進度協定有 task.progress，哨兵沒有人送CaptureChannel 收到第一則回覆就送 progress
圖片／檔案回傳只回文字；圖片變成一行 [圖片 路徑]信封 1 MB 內可以直接帶 base64；大檔要分段
交接的 context 真的被用到context 送到哨兵、記在任務簿，但哨兵跑指令時沒把它交給指令放進子程序環境變數 SYNOX_LINK_CONTEXT 或 AI 的系統提示
per-哨兵指令白名單只有 max_effectconfig link.allow: ["note.*", "cam.*"] 在 WorkerRole.check 多一關
取消盡力：已開始做的做完、不回結果cli pack 要有可中斷的子程序才做得到真正中止
主控台的通知只走 app.notify（Telegram／Discord 私訊）Web UI 對話頁要看到的話，接 web channel
TCP 的握手沒驗過的人連得上、送三次垃圾才被斷要「連 ACK 都不給」就加 Noise IK 握手；內網／WireGuard 裡不需要
安裝精靈link 只能手寫 config.json精靈多一頁「這台是主控台還是哨兵」

要擁有者決定的

D1這一版要不要合進 dev／main？

現在在 claude/charming-einstein-41ih1s，config 不開 link 時行為跟以前一模一樣（install() 直接回 None、沒有指令、沒有執行緒）。

建議：真機清單跑過前半（防火牆、配對、一個任務來回）再合；合的時候 README「還沒有」那一段把「Remote Control／派工」改成「有，alpha，見 docs/link.md」。

D2AI 能不能不經核准卡就派任務？

現在 /link_run 是 WRITE、AI 看得到，所以 AI 說「叫客廳記一筆」會直接派，不出卡；哨兵那邊照它自己的 max_effect 與 authorize 擋。

建議：維持（哨兵有自己的門），但加一個 config link.ai: false 讓不想要的人關掉；DANGER 指令本來就過不了預設的 max_effect。

D3對外聽的 TCP 埠要不要加一層握手（Noise）？

信封已經端對端安全；差別只在「沒鑰匙的人能不能完成 TCP 握手」。內網或 WireGuard 裡沒差；直接開到公網才有差。

建議：先不做，文件明寫「只建議內網／WireGuard」。真的要開公網再做 Noise IK（約 300 行，cryptography 原語都有）。

D4跨網段用 WireGuard，還是自架 relay？

WireGuard 零程式改動、沒有第三方，但兩邊都要裝並管鑰匙；relay 要多一台你的 VPS，但哨兵只要能上網。

建議：WireGuard。等哨兵超過三台或放在別人家再考慮 relay。

D5IoT 的第一個目標是哪個？

攝影機（opencv／picamera2 當哨兵的 pack）、Arduino（pyserial／Firmata）、還是感測器網（MQTT 傳輸）。前兩個不用動 link；第三個要寫 MQTT 傳輸。

建議：先做「門口樹莓派拍照回傳」：驗證樹莓派當哨兵、圖片回傳（上面的缺口）、以及 sandbox 放行裝置檔，三件事一次試到。

D6Telegram 當傳輸層要不要放棄？

調查結論：bot 看不到其他 bot 的訊息，兩支 bot 走不通；要通得用使用者帳號（MTProto），那違反 SYNOX「只是一支 bot」的設計。

建議：放棄。真的想要「不用內網也能通」就是 D4。

D7哨兵的任務要不要留 per-哨兵白名單？

現在只有 max_effect。白名單（link.allow 樣式）更細，但多一個要維護的設定。

建議：先用 max_effect；哨兵上裝了會碰硬體或錢的 pack 時再加白名單。

建議的下一步（照順序）

  1. 兩台 Windows 真機跑「怎麼試」那八步，把結果記進 docs/handoff/（跟 container-verification 一樣的格式）。
  2. 補任務中途進度與圖片回傳（都是哨兵 roles.py 與 CaptureChannel 的小改動）。
  3. 樹莓派哨兵＋攝影機 pack（D5）。
  4. 決定 D1–D7，合併。
