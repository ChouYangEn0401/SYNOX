1. 一句話結論與現況

連動把「等下一次巡邏才發現」改成「狀態一變就接著做」：功能做完時丟出一個小、可存檔的事件，照「資料寫的規則」馬上觸發一個「程式登記過的動作」；不急的排進待處理、等心跳；每一串都帶著「是誰引起的」，再加上循環偵測、層數、頻率、總量與斷路器多層保險，任何失控最多跑幾步就停下、通知一次、看得到原因、可以恢復。

  • 兩份實作都已合併、測試通過。SYNOX 的是通用平台版（系統、工具 pack、設定檔都能定義規則，有網頁主控面板）；bot 的是個人助理版（第一條規則：日記做成圖 → 問今天的日記與靈修要不要打卡）。
  • 骨架一樣、保險的取捨不一樣。SYNOX 偏「平台、未知的程式碼」：登記時就找循環、全部總量上限、只能手動恢復。bot 偏「對人說話、不能嘮叨」：一天只做一次（存檔，重開也不重來）、遵守開口閘、12 小時自動解除。
  • 最根本的限制（兩邊都有）：「是誰引起的」只能跟著同一條執行緒傳（SYNOX 另外也跟著被觸發的任務傳）。動作自己另開執行緒、經過外部程式再回報、或隔一段時間才繞回來的迴圈，會變成新的一串，只能靠頻率與總量上限擋。
  • 建議：寫一份兩邊共用的「連動核心規格」，各自補齊對方有、自己沒有的保險（第 8 節）；先不急著抽成共用套件。
  • 還要做：bot 重開 Host 才會生效、真手機走一次、瀏覽器看一次 SYNOX 主控面板的 🔗 連動卡（第 12 節）。

2. 為什麼要有它：輪詢 vs. 事件

在連動之前，背景任務照間隔跑，心跳（SYNOX 預設每 45 分鐘）叫常駐助理「看一輪」。「A 做完就做 B」只能等下一次排程或心跳，最慢要等一整個間隔；而且每一輪不管有沒有變化都要看一次，看的成本（例如叫 AI）跟變化多寡無關。

連動是另一條路：狀態變化本身就是訊號。變化發生的那一刻寫一筆快速、可存檔的紀錄（SYNOX 是 data/runtime/state.json 的一小塊；bot 是 data/triggers_state.json），符合規則的動作馬上在背景執行緒開始，下一個動作又產生新的變化，形成連鎖反應。不急、需要批次、或想避開打擾的事，留在慢路徑：排進待處理，下一次心跳再一起做掉。

四條設計原則（兩份實作都遵守）

  1. 事件要小、可存檔、不含私人內容。SYNOX 的事件只有任務 id、狀態、標籤、時間；bot 的事件只有來源、結果、幾個小欄位（日期、題組、是不是今天）。內容留在原本的功能裡。
  2. 規則是資料，動作是程式。設定檔只能挑已經登記的動作，不能叫任意指令、不能塞程式碼。要新的動作，得有人寫程式、登記、測試。
  3. 丟事件的一方絕不被拖累。SYNOX 的 listener 在鎖外呼叫、例外只記 log；bot 的 emit 永遠不丟例外。動作都在自己的背景執行緒跑，日記匯出、pack 回報不會被卡住。
  4. 寧可多擋。失控時停下（斷路）、只通知一次、原因看得到、一個按鈕或一行指令恢復。

5. 防失控的原理

「無限連動」有四種形狀，各自需要不同的保險：

  • 環：A → B → A，或自己觸發自己。每一步都很快，會一直轉。
  • 爆炸：一個事件觸發十條規則，每條再觸發十條（寬），或一條接一條很長（深）。
  • 慢性洪水：每一步都合法、也不是同一串，但總量太多（例如外部系統一直回報、或環被打斷成很多串）。
  • 壞掉的動作：每次都失敗，但每次事件來都再試。

5.1 登記時：靜態找循環（只有 SYNOX）

把規則畫成圖：節點是規則；如果規則 A 的動作會讓任務 T 有新狀態（run_task 的那個任務，或程式動作宣告的 emits），而規則 B 在聽 T、標籤也對得上，就畫一條 A → B。圖上有環＝會繞回自己。實作是 settings.find_cycle：三色深度優先搜尋，找到就回傳環上的規則路徑（頭尾同一條），錯誤訊息直接印出來。

  • 寧可多擋：不看 state（ok、failed 都可能），標籤 None（不知道）當作什麼都對得上；run_task 做完的事件沒有標籤（""）。
  • 碰到時：config.json 的規則＝啟動時設定錯誤；系統程式＝丟 RuleError；pack＝不收那一條、記在主控面板「沒有收的規則」，但整個 pack 照常載入。
  • 擋不到：沒宣告 emits 的程式動作（看不到它會回報什麼）、經外部世界繞回來的。這些交給執行時。
  • bot 沒有：動作是不透明的函式，也沒有宣告會丟哪些事件。

5.2 執行時：因果傳遞

每個事件都帶著「這一串」：串 id、第幾層、走過哪些規則。動作開始前把下一層的因果準備好，動作造成的新事件就自動接上。只要一條規則在同一串裡出現第二次，就是環。

因果怎麼傳過去：

路徑SYNOXbot
動作明確地觸發下一件run_now(task, cause=child)：cause 存在任務物件上，任務在另一條執行緒做完時仍帶得出來ctx.emit(source, outcome, …)：chain＝目前 chain＋這條規則
動作裡呼叫別的功能，功能自己丟事件with caused_by(child)（thread-local）：裡面的 report、run_now 自動接上_run 設 thread-local；同執行緒的 bus.emit 自動接上（測試「間接繞回」）
動作另開執行緒、cli 子程序、排程延後接不上 → 新串。兩邊都靠每條規則的頻率上限擋；SYNOX 另外有全部總量。

兩邊的設定都有下限：寫 0 或負數關不掉保險（SYNOX 由 settings.parse 的範圍檢查擋，bot 由 Settings.from_dict 夾在下限）。

5.4 斷路器：停下、通知一次、恢復

  • 通知節流：SYNOX 10 分鐘內只說一則，下一則附「另外還有 N 條也被暫停」；全部暫停另外說一次（之後的檢查先撞到「全部暫停中」，不會重複說）。bot 每條規則每次暫停只說一次（notified 存檔）。
  • 暫停時的待處理（SYNOX）：留著，重設後下一次心跳再做；不會因為暫停就丟掉該做的事。
  • 暫停存檔：兩邊重開都還是暫停的。

6. 讀程式時發現的缺口

以下都是今天讀程式碼時看出來的，都還沒改（這份交接只記錄、不動程式）。嚴重度是對目前用途的判斷。

#在哪缺口目前的影響建議修法
1bot core/triggers.py沒有「同時只跑一個」；once_per 的「做過了」是在動作做完才寫進 done。兩個同一天的匯出幾乎同時進來，兩次 _admit 都會放行。小 checkin_ask 送新的一則時會把舊的收起來，畫面上最多一則開著；但可能多送一則。_admit 通過時先寫「進行中」（或記在記憶體的 running 集合），_run 結束時換成 done 或清掉（pass）。
2bot動作出錯不累計：錯誤只記一行、不算做過，下一個事件會再試。小 受「10 分鐘 5 次」限制；目前事件很稀疏。照 SYNOX：連續失敗 5 次斷路。
3bot沒有全部總量、沒有扇出上限、沒有靜態找循環。小 現在只有一條規則。規則變多就會變重要。見第 8 節。
4SYNOX runtime/activator.py每條規則「這一小時幾次」和全部總量只在記憶體，重開就歸零（暫停狀態有存）。小 一個每次重開都觸發的環，在頻繁重開時可以多跑幾次；仍會被同串偵測擋。把最近一小時的觸發時間也存進 state.json（bot 的 runs 就是這樣做的）。
5SYNOX runtime/heartbeat.py心跳在安靜時段照常執行 drain()；notify 動作直接送出、不看安靜時段。所以「不急的改用 timing: heartbeat」不保證半夜不響。中 目前沒有 heartbeat 時機的 notify 規則；一旦有人照 ADR 的建議寫，就可能半夜送。drain 在安靜時段把 notify 類留著不做（見決定 Q3）。
6兩邊斷路／暫停通知本身不看安靜時段。小 這是系統警告，可能本來就該響；值得明說。維持現狀，寫進共同規格。
7兩邊動作另開執行緒、或經外部程式（cli 工具、打卡系統）回來，因果會斷。中 這是結構性限制；bot 沒有總量上限，只剩每條規則的 5 次／10 分。短期：寫進作者須知（不要在動作裡自己開執行緒）；長期：信封／外部回報可選擇帶回串 id。

7. SYNOX vs. bot 對照與差異的理由

面向SYNOXTelegram bot為什麼不一樣

8. 收斂建議

建議（預設）：先寫一份「連動核心規格」（語意，不是程式），兩邊各自補齊；兩邊各用一段時間、規格不再變了，再考慮抽成共用套件。理由：兩邊的事件模型（任務狀態 vs. 領域事件）和執行環境不同，現在硬抽共用程式，會把兩邊都綁住。

核心規格：每一份實作都應該有的

  1. 事件小、可存檔、沒有私人內容；丟事件永不失敗、不被卡住。
  2. 規則是資料、動作是程式登記的；設定檔不能叫任意指令。
  3. 因果：串 id＋層數＋路徑；明確觸發與同執行緒的間接觸發都要接上。
  4. 五道必備保險：同串同規則（環）、層數、每條規則頻率、全部總量、連續失敗。
  5. 同時只跑一個（或明確選別的模式）。
  6. 需要時的去重：once_per key／day，存檔，判斷「做過」在放行時就佔位。
  7. 結果三態：做了／看過決定不做（都算做過）／現在做不了（不算，下次再試）。
  8. 斷路：停下、通知一次（有節流）、原因看得到、可以手動恢復；自動恢復是規則層級的選項。
  9. 設定有下限，寫 0 關不掉保險。
  10. 計數與暫停都存檔，重開不歸零。

SYNOX 可以從 bot 拿的

  • once_per key／day 去重：之後「問打卡」「每日摘要」這類對人說話的規則一定會用到。
  • 結果三態（sent／skip／pass）：讓「打卡系統叫不到」這種情況不算做過。
  • 頻率計數存檔（修缺口 4）。
  • 可選的自動解除：規則層級的 auto_reset_min，預設關（維持手動，見 Q2）。
  • 對人說話的節制：notify 類在安靜時段留著（修缺口 5）。

bot 可以從 SYNOX 拿的

  • 同時只跑一個＋放行時佔位（修缺口 1）。
  • 全部總量上限：因果斷掉時唯一的跨規則兜底。
  • 連續失敗斷路（修缺口 2）。
  • 動作宣告會丟哪些事件＋載入時靜態找循環：規則變多後，在寫錯的當下就擋。
  • 串 id：log 每一行帶串 id，追「這則訊息是哪一串引起的」比較容易。
  • 扇出上限（便宜，順手加）。

9. 怎麼做

9.1 SYNOX

A. 在 config.json 加一條規則（擁有者自己寫；只收 run_task 或 notify；id 不能用 system.、pack. 開頭；有環＝啟動錯誤）

"runtime": {"activator": {"rules": [
  {"id": "weather-back", "on": "pack.weather", "state": "ok", "from": "failed",
   "notify": "天氣恢復了（{task} {state}）"},
  {"id": "after-sync", "on": "pack.syncer", "tag": "nightly",
   "run_task": "system.schedule", "timing": "heartbeat", "cooldown_s": 600}
]}}

B. 在 python pack 裡加規則（install(app, pack) 裡；規則 id 會是 pack.<名字>.<rule_id>；有環＝不收那一條、pack 照常載入）

def install(app, pack):
    def ask_checkin(event):                       # event.task / state / prev / tag / chain / depth
        app.notify_owner("今天的日記圖片好了。要打卡今天的日記嗎？")
        pack.report_status("ok", "問過打卡了", tag="checkin-asked")   # 自動接在同一串

    pack.on_event("pack.diarydemo", "ask-checkin", ask_checkin,
                  state="ok", tag="diary-image",
                  emits=["pack.diarydemo#checkin-asked"],   # 一定要寫：登記時就能找循環
                  cooldown_s=60, name="日記圖片好了 → 問要不要打卡")

C. 系統程式的規則（id 要 system. 開頭；有環＝丟 RuleError）

from synox import runtime
from synox.runtime.activator import Rule
runtime.of(app).activator.add(Rule(id="system.weather-alert", on="pack.weather",
                                   states=("failed",), do=fn, emits=()))

D. 從新功能丟事件：不用「丟事件」，只要回報狀態。

  • python pack：pack.report_status("ok", "一句話", tag="xxx")
  • cli 工具：SDK report_status("ok", "一句話", tag="xxx")，跟著這次的 JSON 信封送回
  • 系統程式：loop.report("system.x", "ok", "…", tag="xxx")，或註冊成有 fn 的任務，做完自動有事件
  • 標籤：小寫英數字與 . _ -、32 字內；不合格式＝當作沒有。同一個 pack 的不同「做完」一定要用不同標籤，否則自己聽自己。

E. 加一種新的動作（例如「跑一個 pack 指令」——目前刻意不做，見 Q1）。要改的地方：

  1. Rule 加欄位；Rule.check() 寫清楚誰能用（config／系統／pack）。
  2. Rule.emitted()：這個動作會讓哪些任務有新狀態——靜態找循環靠它。
  3. Rule.action_text()：主控面板顯示的字。
  4. Activator._act 加分支，並確保因果傳下去（帶 cause=child 或包在 caused_by(child) 裡）。
  5. 若 config 也能用：runtime/settings.py 的 RULE_KEYS、parse_rule、parse_rules 的 find_cycle 輸入。
  6. web/static/control.js 的文字、docs/runtime-api.md、ADR 0004 的動作表、tests/test_activator.py。

F. 測試（不連網、不開埠；假時鐘、同步執行）

from test_runtime import Clock, FakeApp, sync
from synox.runtime.loop import RuntimeLoop
from synox.runtime.activator import Activator, Rule

def test_my_chain(tmp_path):
    clock, app = Clock(), FakeApp()
    loop = RuntimeLoop(app, clock=clock, spawn=sync, state_path=str(tmp_path / "state.json"))
    act = Activator(loop, settings={"max_depth": 2})        # 想測哪道保險就把上限調小
    act.add(Rule(id="system.a", on="pack.a", notify="收到 {task}", owner="system"))
    loop.report("pack.a", "ok", owner="a")
    assert app.sent == ["🔗 收到 pack.a"]
    clock.advance(minutes=11)                                  # 測冷卻、頻率、通知節流
    assert act.view()["rules"][0]["status"] == "active"

要測「上一次還沒做完」：把 loop._spawn 換成只把函式收進清單、不執行。整個 bot 的整合測試用 rt_bot fixture（見 test_example_diary_image_done_asks_checkin_via_pack）。

G. 除錯一條被暫停的規則

  1. 手機上會收到一則「⏸ 連動規則「…」暫停了：原因」。
  2. 打開網頁主控面板的「🔗 連動」卡：每條規則的狀態徽章、暫停原因與時間、上次觸發、這一小時幾次、連續失敗；「最近的連動」列出每個事件的串 id、層數、做了哪些、略過哪些與原因。
  3. 或 GET /api/runtime/status 的 activator：rules[].reason、events[].chain/depth/fired/skipped、rejected（登記時就沒收的）、budget_used。
  4. 原因是「循環」：照事件的串 id 把同一串的事件排起來，就是那個環；改規則（換標籤、加 from、改成 notify）。
  5. 修好後按「重設」（POST …/activator/rules/<id>/reset）；全部暫停的按「恢復」。暫停中的待處理會在下一次心跳做掉，不想要就按「不用做了」。
  6. synox doctor 也印開關、規則數、暫停中的規則、待處理件數。

9.2 Telegram bot

A. 改規則或加規則（資料檔；改了就生效，不用重開）

// data/triggers.json（這台電腦）：同一個鍵蓋過 defaults
{"rules": {"diary_image_checkin": {"enabled": false}}}

// 新規則（defaults/triggers.json 進版控，或只放 data/）
{"rules": {"my_rule": {
  "enabled": true,
  "when": {"source": "diary.export", "outcome": "image", "data": {"is_today": true}},
  "do": "checkin_ask",
  "args": {"habits": ["日記"], "ttl_min": 120},
  "once_per": "key",          // key＝同一個範圍一次；day＝每天一次；不寫＝不限

規則 id 以 _ 開頭的會被忽略（拿來寫註解）。do 指到沒登記的動作＝記一行 blocked:no_action。

B. 加一個新動作

from <bot 套件>.core.triggers import PASS, SENT, SKIP, Result

def my_action(event, rule, ctx):        # 在自己的背景執行緒跑
    if not ready():
        return Result(PASS, "not_ready")        # 這次不算，下一個事件可以再試
    if nothing_to_do():
        return Result(SKIP, "nothing")          # 看過、決定不做；算做過（once_per 不再試）
    do_it(ctx.args)
    ctx.emit("my.feature", "done", {"day": event.key}, key=event.key)   # 要接下一件就用 ctx.emit
    return Result(SENT)

# main.build 裡
triggers.action("my_action", my_action)
  • 會主動開口的動作：先過開口閘（companion.may_speak()），被擋就記中性紀錄、回 skip；照通知分流表標流與 kind，並在 docs/notifications.md 加一列。
  • 送出的按鈕綁既有的節點（例：now.check），不另做權限；要「替他執行指令」的動作得走 dispatcher 並以擁有者身分授權（invariant 6）。
  • 不要在動作裡自己開執行緒去丟事件（因果會斷，見缺口 7）。
  • invariant 22 的「現在的規則」那一行要更新。

C. 從新功能丟事件：在功能做完的地方（例：DiaryDesk._emit_done）

if self.triggers is not None:
    from <bot 套件>.core.triggers import Event
    self.triggers.emit(Event("my.feature", "done",
                             {"day": day, "is_today": day == today},   # 只放小欄位，不放內容
                             key=day))                                  # 這件事的範圍

並在 main.build 把 bus 接給那個 desk（desk.triggers = triggers）、在 defaults/triggers.json 的 _doc 寫上這個新事件的 source／outcome／data。

E. 除錯一條被斷路的規則

  1. 手機收到「⛔ 連動「…」停下來了：原因」，附暫停到幾點與 reset 指令。
  2. /sys_triggers：每條規則（● 開、○ 關、⏸ 暫停）、暫停到幾點與原因、保險設定、最近 10 行紀錄。

10. 業界前例

系統它怎麼做這裡拿來用的
Home Assistant automations每個 automation 有 mode：single（預設，還在跑時新的觸發不開）、restart、queued、parallel；事件帶 context（id＋parent_id）SYNOX 的「同時只跑一個」；事件帶因果
GitHub Actions用 workflow 自己的 token 觸發的事件不會再開新的 workflow（防遞迴）；reusable workflow 有巢狀層數上限層數上限；同串同規則不能再出現
Apache AirflowDAG 一定無環，解析時就檢查；trigger rule（all_success、one_failed…）決定下游何時跑登記時靜態找循環；條件寫成「變成哪個狀態、從哪個狀態來」
Zapierflood protection：一次來太多觸發就先扣住，讓人決定放不放行全部總量上限 → 全部暫停、等人按恢復
斷路器模式（circuit breaker）一直失敗就斷開；過一段時間「半開」試一次，成功才閉合斷路＋通知一次；半開兩邊都還沒做（bot 是時間到直接閉合）

刻意不照抄的：Home Assistant 的 queued／parallel（現在沒需要）、Zapier 的「每一筆扣住等放行」（改成整條暫停＋待處理留著，比較好懂）、完整的工作流程引擎（太大，這裡只要「做完 → 做下一件」）。
