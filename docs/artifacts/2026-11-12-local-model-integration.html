本地模型接法調查

2026-11-13 改寫 · 只讀程式與文件，沒有跑任何模型、沒有開埠 · 舊版以「讓 Claude Code 轉本地模型」為主軸，方向錯了，整份重寫

結論

  • 可以用本地模型（Ollama）取代 Claude 來回話和呼叫工具。
  • 做法是換掉 SYNOX 的模型接口 ChatAdapter。授權、確認卡、執行工具都是 SYNOX 自己做的，跟模型是誰無關，所以不用動那些。
  • SYNOX 現在就接得上：llm.kind 選 openai_compat，base_url 填 http://localhost:11434/v1。模型不會原生工具呼叫時，還能退到文字協定。
  • 缺的是驗證和防呆：沒人測過本地模型在 SYNOX 裡表現如何；連線、模型有沒有拉、context 夠不夠，現在都沒有事先檢查。
  • 下一步：到學校電腦（有 Ollama）照測試單跑一輪，先不改程式（選項 A）。測試單在 SYNOX_Plans 的 _inbox/20261113-005821-local-llm-school-test.md。

架構：模型只是被換掉的那一塊

綠色區塊是 SYNOX 自己的程式，換模型完全不受影響；紫色區塊是可以替換的模型。兩邊之間只有一個接縫，就是 ChatAdapter：SYNOX 把對話和工具清單交出去，模型回「一段話」或「我想呼叫某個工具、參數是什麼」。真的去執行，永遠是 SYNOX。

SYNOX 的程式，換模型不變 模型，可替換

設定位置：src/synox/llm/factory.py 依 llm.kind 選 adapter（none／fake／openai／anthropic／gemini／openai_compat 經 ntu_easy_llm；claude_code 走文字協定）。介面定義在 src/synox/llm/base.py，文字協定在 src/synox/llm/textproto.py。

風險與對策

接線本身不難，真正的風險是本地模型夠不夠聰明。

風險會發生什麼現在能做的之後可補（選項 B）
工具呼叫的 JSON 寫壞小模型常見。文字協定解析不到，使用者會看到一段亂碼似的回答；不會執行錯的東西學校測試記錄壞掉的比例，比較原生與文字協定解析失敗時重試一次，再失敗就說「沒聽懂」，不硬執行
選錯工具、參數錯唯讀工具就是答錯；寫入類（加行程等）會先跳確認卡，人可以拒絕測試單第 4 類「故意含糊」的題目專測這個依測試結果決定要不要縮小給本地模型的工具清單
context 不夠系統提示＋soul.md＋工具清單＋歷史被截掉，模型忘記規則或工具Ollama 的 context 設 65536（至少 32768）探測時讀模型的 context 長度，不夠就不啟用並說明原因
錯誤發現得太晚網址填錯、模型沒拉，沒按「測一下」的話，要第一次聊天才看到「AI 沒有回應」設定完一定先按「測一下」啟動時做只讀探測，在設定頁和 doctor 直接顯示
危險動作被放行不會。確認卡是 SYNOX 的，不是模型的，換模型照樣跳測試單第 3 類題目確認卡片有出現不需要

為什麼不走 mvpPipelineStudy 那條路

mvpPipelineStudy（核心在 mvp/env/runtimes.py、說明在 docs/design/runtimes.md）是開 Claude Code 這支程式去操作專案，跑指令、改檔案都是 Claude Code 在做。所以它要用本地模型，只能讓 Claude Code 繼續當執行者、把模型請求轉到 Ollama。

SYNOX 不是這樣：執行者是 SYNOX 自己，模型只負責回話。直接換 ChatAdapter 就好，不需要經過 Claude Code。舊版報告的「讓 Claude Code 轉本地」整個拿掉。

可以借的只有兩件事

  • 只讀探測：打 Ollama 的 /api/version（版本）、/api/tags（模型拉了沒）、/api/show（capabilities 有沒有 tools、context 長度）。不叫模型回答，2 秒逾時，結果快取 30 秒。
  • 能力不足就不啟用：不會工具、或 context 小於 32768（建議 65536），就在開始前講清楚原因，不要等聊天時才壞。

選項（請選一個）

選項一句話
A. 只測，不改程式在學校電腦照測試單跑一輪，寫成測試紀錄，看本地模型哪裡會壞建議（預設）
B. 測完再加連線檢查依 A 的結果在 SYNOX 加 Ollama 只讀探測，以及工具呼叫解析失敗重試一次再回報、不硬執行等 A 的結果再決定
C. 用評分題庫跑用 evals/assistant 的題目替本地模型評分範圍大，A 之後再說

選 A 的理由：程式已經接得上，現在不知道的是模型靠不靠得住。先測再改，才知道 B 要補哪些。測試單裡寫的「上一份調查的選項 B 已作廢」指的是舊版的「Claude Code 轉本地」；這一版的 B 是新的內容，與測試單一致。

測試單

SYNOX_Plans 的 _inbox/20261113-005821-local-llm-school-test.md，狀態「待處理」，要在學校電腦做；家裡這台不跑模型、不開埠。

步驟摘要（選項 A）

  1. 在學校電腦看 Ollama 版本與模型，挑一個支援工具的（例如 qwen3-coder、gpt-oss:20b，看裝得下哪個），context 設 65536。
  2. SYNOX 的 llm 設成 openai_compat、base_url 填 http://localhost:11434/v1、tools: true。
  3. 按精靈的「測一下」，記下成功或錯誤訊息。
  4. 用程式內的假 Telegram 依序問四類題目：一般問答、唯讀工具（查待辦）、要確認卡的（加行程）、故意含糊容易選錯工具的。
  5. 原生工具呼叫不穩，就改 tools: false 再跑一次，比較兩種。
  6. 每題記下：選了什麼工具、參數對不對、JSON 有沒有壞、花多久、context 有沒有被截。

驗收

  • 有一份測試紀錄放在 SYNOX_Plans 的 docs/，每題有輸入、模型實際的工具呼叫、對或錯。
  • 明確寫出這個模型在原生與文字協定下哪個可用、哪幾類題目會壞。
  • 沒做或做不到的步驟寫清楚原因，不寫成通過。

測試時的界線：Ollama 只聽本機、不開埠給外面、不動防火牆；不帶家裡的資料、金鑰、token 過去，用假資料；一次只開一個模型；選項 A 不改 SYNOX 程式，紀錄不放進 SYNOX 的 dev／main。

沒驗證的事

  • 以上全部來自讀程式與文件。這台電腦沒有跑任何模型或服務，沒有開埠，也沒有改程式或建分支。
  • 沒查原生工具呼叫模式下，ntu_easy_llm 收到格式壞掉的工具呼叫會怎麼處理；表中「解析失敗就把原文送出」只針對文字協定。
  • 不知道 SYNOX 系統提示＋soul.md＋工具清單實際多少 token，所以 context 夠不夠是推測，要學校測試確認。
  • mvpPipelineStudy 那邊的 Ollama 直連也沒有實測紀錄（文件寫只有假伺服器測試，另有一次 vLLM 實測），探測做法借過來也要自己測。
