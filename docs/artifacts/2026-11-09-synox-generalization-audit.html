4 · 安全架構：資料在誰手上、LLM 怎麼換、能不能在 Telegram 端加密 架構定稿・demo 建置中

2026-11-10 改寫：你糾正得對，層要拆開

第一批這裡寫「Telegram 不是端對端、LLM 要看明文，所以加密沒用」，把兩件事黏在一起了。拆開之後是四個會看到內容的位置，各自能不能擋不一樣（全文 docs/plans/2026-11-10-synox-architecture-v1.md）：

  • ① Telegram 平台看到你打的字——擋不了，用 Telegram 的代價。
  • ② 跑 bot 的程序看到同樣的字——看它在誰的機器上：你自己的電腦＝只有你；營運者的伺服器＝營運者。
  • ③ 存起來的資料——可以完全對營運者保密：金鑰在使用者自己的裝置產生、伺服器只存密文（不能拿 Telegram 身分當金鑰，營運者知道身分）。
  • ④ LLM 供應者看到提示——擋不了「供應者看到」，但可以決定由誰送（使用者的裝置直接送，不經營運者）、送給誰。

結論：A、B、C 三條都做、安裝時就選。A 與 B 是同一個安裝包（差在 AI 頁填誰的端點），所以精靈只問「個人版／伺服器版」；伺服器版再分 C1 托管資料（營運者②③④都看得到，要講清楚）與 C2 加上 SYNOX Node（使用者自己的裝置持金鑰、跑 pack、送 LLM；營運者只看到②，用 Web UI 聊天時連②都看不到）。Node 這一輪只定規格。

拓樸資料庫在LLM 是朋友公司看得到適合誰建議
A 本機優先自己電腦，落地加密（DPAPI 綁 Windows 帳號）自己的（Claude Code／API key／Ollama）什麼都看不到電腦常開、自己有 AI 來源的人預設
B 本機 host＋別人的 LLM自己電腦，落地加密朋友公司的端點（adapter openai_compat）你送出的問句＋工具回傳給 AI 的那幾行；看不到資料庫、看不到聊天全文沒有訂閱、沒有 key 的人（你朋友的情境）給沒 AI 的人；要更保守就本機模型
C 整個 host 架在朋友公司公司伺服器公司的一切：營運者有 bot token、有資料庫、有 LLM 日誌。每人一把金鑰加密只防「資料庫被偷走」，防不了營運者電腦不常開、又不介意公司看到的人只在講清楚的前提下做；用 Telegram Managed Bots 發行、每人一個隔離實例
