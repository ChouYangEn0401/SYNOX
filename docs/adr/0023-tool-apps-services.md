# ADR 0023：工具服務——每個工具可以開一個自己的完整網頁，要用才開、不用就關

- 日期：2026-11-14
- 狀態：**提案，等擁有者核准**。這份文件裡沒有任何一行程式已經寫了；核准之前不動 `src/`。
- 基準：分支 `dev`，commit `b5f48e2`。文中的 `檔案:行號` 都是這個 commit 的。
- 分工：[實作計畫](../lab/2026-11-14-tool-apps-implementation-plan.md)（八個工作包，WP0–WP7）。工具那一側：SYNOX_Libs 的 `docs/adr/0003-tool-apps-and-money-app.md`。
- 標籤（沿用 [ADR 0022](0022-ecosystem-bridge-and-sandbox.md)）：**已查證**（讀過程式或 0022 研究的一手來源）／**推測**（照規格推的）／**待實測**（要在真的瀏覽器上看）／**提案值**（數字是這份文件定的，可以改）。
- 平台現實：**維護者的開發機不准開任何網路埠、不准動防火牆**。這份設計的每一塊都能用「直接呼叫函式」驗證；真的開埠、真的用瀏覽器點，只有擁有者帶到別台電腦才做（計畫第 9 節的清單）。

> **先講清楚：這個功能本身會開埠。** 擁有者按下「開啟服務」時，SYNOX 會在 `127.0.0.1` 多聽一個埠（預設 8841 起）。
> 只有這台電腦連得到、不碰防火牆；沒按就不開，SYNOX 重開之後一律都是關的。

## 擁有者要的（協調者轉述；原話補上時請一字不改貼在這裡）

- SYNOX_Libs 的工具（記帳、行事曆、待辦、筆記、子彈筆記…）裝進 SYNOX 之後，每個也要是一個「自己的 app」，有完整的網頁畫面。
- 在 SYNOX 主機台（網頁，Telegram 也要）可以「開啟某個工具的服務」：開一個埠、放那個工具的畫面，用瀏覽器看與改資料（例如完整的記帳網頁）；也可以關掉。
- 主機台隨時看得到哪幾個工具的後端開著，並建議把沒在用的關掉——沒在用就不該有東西在聽。
- 模型是「像我本機的 Telegram」：Telegram 負責下指令（記一筆、加行程），每個工具另外有畫面可以看；不用就關，就沒有資安風險。
- **一般使用者要看得懂**：什麼是「服務」、為什麼要關。

## 給使用者的說法（畫面上的字照這個寫；草稿）

| 名詞 | 一句話 |
|---|---|
| 工具服務 | 「記帳平常只在 SYNOX 裡面聽你的指令。**開啟服務**＝SYNOX 在這台電腦上多開一個網址，讓你用瀏覽器看完整的記帳畫面。這個網址只有這台電腦打得開。」 |
| 為什麼要關 | 「服務開著，就像家裡多開了一扇門：沒有你的登入進不來，但門在那裡。不用的時候關上，門就不存在了。**關掉不會刪任何資料**，Telegram 照樣可以記帳。」 |
| 重開之後 | 「SYNOX 每次重開，所有服務都是關的；要用再開。」 |
| 動作的三種標示 | 沿用工具頁現有的字：唯讀／會寫入／危險：會先問你（`src/synox/web/static/tools.js:14`）。 |

主流程的字不出現 port、session、CSRF、origin 這類詞（「埠」只放在小括號或「進階」）；同 0022 的 R6、R7。

## 1. 誰來開這個埠

現況（**已查證**）：網頁介面是標準函式庫的 `ThreadingHTTPServer`，只綁 `127.0.0.1:8830`（`src/synox/web/server.py:63`、`:257-285`）；所有判斷在 `WebUI.route()`，
`_Handler` 只是讀進來、呼叫 `server.ui.handle(...)`、寫回去的薄殼（`server.py:1735-1759`）。kind=python 的工具本來就在 SYNOX 的程序裡跑，
資料經 `pack.store.of(user)` 進保管箱（`src/synox/packs/loader.py:76-134`）。

| 選項 | 做法 | 結論 |
|---|---|---|
| **A（建議）** | SYNOX 在自己的程序裡，替每個開著的 app 再開一個 `_Server`（同一個薄殼、同一個綁定規則），交給一個只服務那個工具的 `AppSite` | 採用 |
| B | 不開新埠，放在 8830 的 `/apps/<名字>/` 底下 | 不採用：跟主機台同一個來源，工具的畫面程式拿得到主機台的防偽造 token、能做擁有者能做的任何事——就是 0022 的 R4 點名「不能沿用」的 `web.panel` 問題（`tools.js:375`、`server.py:504-514`）。而且「關掉」只是邏輯開關，埠還在 |
| C | 每個工具自己跑一支伺服器程序 | 不採用：（1）保管箱的金鑰要交給工具，或另外發明一條取資料的通道；（2）**瀏覽器的 cookie 不分埠**（**已查證**，0022 研究 [WB7]）：主機台的登入 cookie 會被瀏覽器原封不動送到工具的那個埠——等於把主機台的登入交給工具的程序；（3）伺服器版「這個請求是誰」要每個工具重做一次；（4）工具得宣告連網與開程序兩種能力，第 2 關的意義就沒了 |
| D | 全部 app 共用第二個埠（8831），用路徑分 | 不採用：app 之間同一個來源、互相不隔離；「只關記帳」關不到埠 |

A 的性質：

- **金鑰不動**：app 的讀與寫都只是呼叫工具已經登記的函式，`fn(user, …)` 裡照舊用 `pack.store.of(user)`。工具拿到的東西跟今天一模一樣。
- **伺服器版**：請求是誰由 SYNOX 的 app 登入決定，資料照舊每人一份。對外網址（`web.public_url`，反向代理）**第一版不轉發 app 的埠**——app 只能在跑 SYNOX 的那台電腦上開。
- **綁定規則只有一份**：新埠一律用 `server.bind_host()`（`server.py:187-207`）與 `_Server`（Windows 獨佔綁定，`server.py:1721-1732`）；不新增任何改綁方式（AGENT.md invariant 9）。
- **容器（Docker）**：compose 目前只發佈 8830（`docker-compose.yml:34`）。第一版在容器裡**預設不開放這個功能**（狀態寫「容器版還沒開放工具服務」），之後要開再加一段只發佈到宿主 `127.0.0.1` 的埠範圍（計畫的「之後」）。
- **負擔**：每個開著的 app 多一條等連線的執行緒；沒有 app 開著時，連定時檢查都不排（第 4 節）。同時最多開 3 個（提案值）。

## 2. 寫入：一個動作＝一個指令

現況（**已查證**）：`web.api` 只有 GET、`fn(user)` 沒有參數（`src/synox/packs/manifest.py:362-389`、`loader.py:196-201`、`server.py:883-891`）。
指令的欄位、檢查、危險程度都掛在葉節點上：`kit.command(group, 名字, fn, …, effect=, fields=[Field(..., check=)])`（`src/synox/packs/kit.py:172-193`），
權限的唯一交會點是 `policy.decide`（接在 `registry.authorize`，AGENT.md invariant 11）。

決定：

1. **app 的動作一定對應同名的指令**。`pack.json` 的 `web.app.actions` 寫 `{"rm": "DANGER", "add": "WRITE"}`；工具用
   `pack.app_action("rm", fn)` 掛 `fn(user, values) -> dict`。SYNOX 載入時核對：這個群組底下有沒有叫 `rm` 的葉節點、它的 `effect` 是不是跟宣告的一樣；
   不一樣＝這個 app 整個不掛（fail closed），doctor 與狀態頁寫原因。
2. **欄位檢查只有一份**。動作收到的 `values` 用那個葉節點的 `fields` 檢查——把 `kit.parse_args` 後半段（`choices`、`check`、預設值、缺必填，`kit.py:156-169`）
   抽成 `kit.check_values(fields, values)`，Telegram 那條與 app 這條都叫它。錯誤訊息因此一字不差。
3. **權限只有一份**。`app.registry.authorize(user, node, TYPED, user.tg_id)`——角色、能力上限、伺服器版 `data: shared` 的寫入要管理員，全部照舊，不在 app 這邊另寫判斷。
4. **危險的動作強制兩步**。第一次送出不帶確認 → 伺服器回 409 與一張一次性的確認票（綁這次登入、這個動作、這組參數的雜湊，60 秒）；
   共用元件畫確認框（文字由伺服器給），使用者按「確定」才帶票重送。對應 AI 那條的核准卡（security.md 第 5 關）。
5. **防偽造**：非 GET 一律要 app 自己的 `X-SYNOX-CSRF`、`Content-Type: application/json`，再加第 3 節的來源檢查。
6. **稽核**：每個動作一行寫進 `data/apps_audit.jsonl`——時間、誰、哪個 app、哪個動作、危險程度、成功與否、有沒有確認。**不記參數的值**（金額、備註在保管箱裡是密文，不能明文流進紀錄檔）。
7. **讀**：`web.app.reads` 列名字，`pack.app_read("entries", fn)` 掛 `fn(user, params) -> 可轉 JSON`（`params` 是網址列的查詢參數，全是字串）。只回這個人自己的，規則同 `web.api`。

工具端的寫法因此是「一個核心函式、兩個薄殼」：指令把結果排成一則訊息，動作把同一個結果原樣回成 JSON。記帳的具體拆法在 SYNOX_Libs ADR-0003。

誠實說明：兩步確認擋的是**手滑與單一請求的偽造**，擋不了惡意的畫面程式（它可以自己按第二步）。惡意畫面的邊界是第 3、5 節。

## 3. 登入與隔離

### 3.1 關鍵事實：埠隔得開「來源」，隔不開 cookie

- 同源政策看「協定＋主機＋埠」：`127.0.0.1:8841` 的畫面程式讀不到 `127.0.0.1:8830` 的頁面內容與回應（**推測**自規格；待實測）。這是選獨立埠的主因。
- cookie 只看主機、不看埠（**已查證** [WB7]）；瀏覽器眼中 `127.0.0.1` 的每個埠是「同一個網站」（same-site），所以 `SameSite` 屬性擋不住「埠對埠」的請求（**推測**自規格）。

後果與對策（全部列進實作計畫，缺一不可）：

| 風險 | 對策 |
|---|---|
| app 的畫面程式對主機台（8830）送寫入請求，瀏覽器會自動帶上主機台的 cookie | 主機台現有的兩道照舊擋得住：`Origin` 的主機與埠要等於 `Host`、要帶 session 的 CSRF token（`server.py:374-382`；token 只從 `/api/me` 的 JSON 給，app 那邊讀不到）。**新增第三道**：`/api/*` 收到 `Sec-Fetch-Site` 是 `same-site` 或 `cross-site` 一律 403（工作包 0） |
| app A 的畫面程式打 app B | 每個 app 埠同樣三道：Host 白名單、`Origin`＝自己、`Sec-Fetch-Site`＝`same-origin`；寫入另要 app 自己的 CSRF token。回應加 `Cross-Origin-Resource-Policy: same-origin`，永遠沒有 `Access-Control-*` |
| app 的畫面程式用 `document.cookie` 塞一個同名的假 cookie，讓主機台的請求變成沒登入（搗亂） | 主機台與 app 讀 cookie 時「同名的每一個都試，第一個有效的算數」（現在只看第一個：`server.py:175-180`）。工作包 0 |
| 從主機台開新分頁，app 拿到 `window.opener` 把主機台那一頁導去別處 | 一律用 `noopener` 開；主機台與 app 的回應都加 `Cross-Origin-Opener-Policy: same-origin` |
| DNS rebinding（外面的網域解析到 127.0.0.1） | app 埠每個請求先查 `Host` 只能是 `127.0.0.1:<埠>` 或 `localhost:<埠>`，其他一律 403、不回內容 |
| 畫面程式把資料帶到外面 | 內容安全政策擋掉連外、內嵌程式、外部資源（下面 3.3）；**擋不住「整頁導去外站」**（見「擋不住的」） |

備選（寫下來，不是第一版）：每個 app 用自己的主機名 `http://money.localhost:8841/`。主機名不同，cookie 就真的分開、瀏覽器也當成不同網站。
但它靠瀏覽器自己把 `*.localhost` 解析到本機（各瀏覽器行為**待實測**），所以先不賭；擁有者在別台電腦實測可行，再換（要擁有者決定的第 4 題）。

### 3.2 怎麼進去

- **app 有自己的登入**：cookie 名 `synox_app_<名字>`（HttpOnly、SameSite=Strict、不設期限＝關瀏覽器就沒了），伺服器端只放記憶體。
  服務一關，這個 app 的登入全部作廢；它的 CSRF token 跟主機台的不是同一個——畫面程式拿到的 token 在主機台沒有用。
- **進門的三條路**（都只在「瀏覽器直接開 `GET /`」時發生，API 請求不會發登入）：
  1. 已經有這個 app 的登入 → 直接進。
  2. 這個瀏覽器已經登入主機台（主機台的 cookie 會被送過來，接的是 SYNOX 自己的程式，不是工具的）而且這個人看得到這個工具（`registry.visible`）→ 發一個 app 登入。
  3. 個人版、`web.local_auto_login` 開著、而且是使用者自己在網址列／書籤／外部程式開的（`Sec-Fetch-Site: none`…，跟主機台同一條規則：`server.py:358-364`）→ 以擁有者發一個 app 登入。
  都不是 → 一頁白話：「請先從 SYNOX 打開」，附回主機台的連結。
- **所以連結裡沒有任何秘密**：主機台的「打開」按鈕與 Telegram 的 `/app_open money` 給的都是 `http://127.0.0.1:8841/`，轉給別人也沒用，不必經 Telegram 傳一次性金鑰。
- **埠固定**：每個工具第一次開時從 8841 起配一個、記在 `data/apps.json`，之後都用同一個（書籤才有用）；被占用才換下一個並告訴使用者。
- **全頁，不放 iframe**：app 的回應 `X-Frame-Options: DENY`、`frame-ancestors 'none'`。共用元件在頁首畫一條固定的列：工具名、登入的是誰、「回 SYNOX」、「關閉服務」。

### 3.3 app 埠的回應標頭（提案）

`Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`，
加上現有的 `nosniff`、`no-referrer`、`no-store`（`server.py:91-92`）與 `X-Frame-Options: DENY`、`Cross-Origin-Opener-Policy: same-origin`、`Cross-Origin-Resource-Policy: same-origin`。
沒有 `'unsafe-inline'`：畫面程式一定在檔案裡，檔案都在 `packs.lock` 的雜湊裡。

### 3.4 靜態檔怎麼送

開啟服務的那一刻，把 `web.app.root` 底下的檔讀進記憶體、**逐檔對 `packs.lock` 的雜湊**，對不上＝不開、說是哪個檔。之後只從這份記憶體快照回應（用正規化後的相對路徑查表），
請求的路徑永遠不會碰到檔案系統，所以沒有 `..` 可鑽。沒登入拿不到任何檔。

## 4. 開、關、狀態、提醒

| 項目 | 決定 |
|---|---|
| 狀態 | `off` 關著｜`on` 開著（埠、開了多久、多久沒用）｜`error` 開不起來（一句原因＋下一步） |
| 誰能開關 | 擁有者（伺服器版也是；成員只看得到「開著、可以打開」）。**AI 與常駐助理可以列出、可以關，不能開**（`/app_open` 設 `ai=False`）：多開一扇門這件事只收人下的令 |
| 第一次開 | 主機台先顯示上面那三句說明，按「知道了，開啟」才開；之後不再問 |
| 看得到的地方 | （1）主機台側欄常駐標記：有服務開著時顯示「● 1 個工具服務開著」，點了看清單與「關掉」「全部關掉」；（2）工具頁每個有 app 的工具一張卡：狀態、「開啟並打開」／「打開」／「關掉」、「這是什麼？」；（3）主控頁的任務清單多一列 `system.tool_apps`（常駐助理因此也知道）；（4）Telegram `/apps`；（5）`doctor` 一行（設定＋上次執行留下的狀態檔） |
| 算「有在用」 | 進門、讀資料、做動作、按「先留著」。共用元件**不做背景輪詢**（開著分頁不算在用） |
| 閒置 | 30 分鐘沒用 → 提醒一次（主機台標記變色＋Telegram 一則：「記帳的服務 30 分鐘沒用了，要關就 `/app_close money`；不理我的話再 90 分鐘我會自己關」）；滿 120 分鐘 → 自動關、記稽核、留一行通知。`web.apps.idle_close_min: 0`＝永不自動關；`idle_suggest_min: 0`＝不提醒 |
| 定時檢查 | 登記成 runtime 任務 `system.tool_apps`（AGENT.md invariant 18），每 60 秒；**一個都沒開時不排**（`reschedule(None)`） |
| 一定會關的時機 | SYNOX 結束／重開（不保存「開著」的狀態）、`/web_off`、那個工具被重新載入／升級／移除／健康檢查隔離、檔案跟鎖對不上 |
| 關掉做什麼 | 停止聽、關埠、作廢這個 app 的所有登入與確認票、寫稽核、更新狀態檔。分頁還開著的人下一次操作會看到共用元件的遮罩：「這個服務已經關了。回 SYNOX 再開一次就好，資料都在。」 |
| 稽核 | `data/apps_audit.jsonl`：開、關、自動關、提醒、進門、每個動作、被拒絕的請求（原因碼）。1 MB 換檔、留一份舊的。主機台卡片與 `/apps` 顯示最近幾筆 |

## 5. pack 怎麼宣告

```json
"web": {
  "panel": "panel.html", "api": ["GET /summary"],
  "app": {
    "entry": "app/index.html", "root": "app", "title": "記帳本",
    "reads": ["month", "entries", "categories"],
    "actions": {"add": "WRITE", "edit": "WRITE", "rm": "DANGER"}
  }
}
```

- **共存，不搬**：`web.panel`／`web.api` 一個字都不改（工具頁裡的小摘要）。它跟主機台同源的問題仍由 0022 §5.7（決定 23）處理；app 這條路從第一天就是隔開的。之後 panel 要不要改成「打開 app」的入口，等 0022 定案。
- **第 1 關**（`manifest.py`）：只收 kind=python（第一版）；`root` 是 pack 裡的一個子資料夾、`entry` 是它裡面的 `.html`，路徑規則照 `web.panel` 那套，並加進 UNC 檢查清單（`manifest.py:159-190`）；
  `root` 底下只准白名單副檔名（`.html .js .css .json .png .jpg .jpeg .webp .svg .ico .woff2`）、最多 100 個檔、單檔 512 KB、合計 3 MB（提案值）；`reads` 的名字、`actions` 的名字與值（只收 `WRITE`／`DANGER`）。
- **第 2 關**（新檔 `packs/appscan.py`，只用標準函式庫、不執行）：
  - **擋（列檔名:行號）**：HTML 裡有內容的 `<script>`、`on*=` 屬性、`<base>`、`<meta http-equiv>`、`<iframe>`／`<object>`／`<embed>`；任何檔裡的對外網址（`http://`、`https://`、`//主機`；`http://www.w3.org/` 的命名空間除外）；CSS 的 `@import`；入口頁沒有載入 `/_synox/kit.js`。
  - **只提醒**（0022 R3：看不懂 JS，樣式比對不當門）：`eval`、`new Function`、`document.cookie`、`window.open`、改 `location`、`sendBeacon`、`WebSocket`。
  - `root` 底下的 `.js` **不算**「掃不到內容的程式」（現在 `.js` 一律算、會被判 T2 並要宣告 `exec`：`scan.py:174-192`）——它不在這台電腦上執行，是在瀏覽器裡。條件是 `root` 底下沒有白名單以外的檔。信任層級不變。
- **安裝報告**多一段白話（一定顯示）：「這個工具附了完整的網頁畫面（N 個檔）。它在你的瀏覽器裡跑，能讀寫這個工具自己的資料（下面列的動作）。SYNOX 檢查了格式、擋了連到外面的網址，但**看不懂畫面程式在做什麼**——跟 `pack.py` 一樣，是你決定要不要信任的程式。」下面列每個動作與危險程度。
- **升級紅字**（`upgrade.py`，接在「新加網頁面板」那條旁邊：`upgrade.py:159-160`）：新加了完整網頁畫面；動作變多；動作的危險程度變寬。
- **SDK 版本**：只加新東西 → `SDK_VERSION` 0.2.2 → 0.2.3。附 app 的工具要寫 `requires.sdk: ">=0.2.3,<0.3"` 與新的 `requires.synox`（舊的 SYNOX 會把 `app/*.js` 判成 T2）。

## 6. 畫面技術

- 純 HTML／CSS／JS，沒有建置步驟、沒有框架、沒有 CDN、只用系統字型（離線可用，也是 3.3 那條 CSP 的前提）。
- **共用元件由 SYNOX 提供**，每個 app 埠都有 `/_synox/kit.js`、`/_synox/kit.css`：
  - 顏色與字級沿用主機台的設計 token（淺色、深色），所以 app 看起來是 SYNOX 的一部分；
  - `SynoxApp.read(名字, 參數)`、`SynoxApp.act(名字, 值)`（自動帶 CSRF、處理兩步確認、把錯誤變成白話提示、服務關了顯示遮罩）、`toast`、`confirm`、依欄位定義產生表單（欄位說明來自同一份 `Field`）；
  - 頁首那一列（工具名、誰、回 SYNOX、關閉服務）。
- 為什麼放 SYNOX 不放進每個工具：一份、跟著 SYNOX 更新；防偽造與確認的邏輯不該每個工具各抄一份。
- 文字一律 `textContent`、不用 `innerHTML`（主機台現有的規矩）。

## 7. 測試（配合開發機的限制）

- `AppSite.handle(method, target, headers, body)` 與 `AppManager` 都是不碰 socket 的物件；真的開埠只有 `listen.open_listener()` 一個小函式，`AppManager(listen=假的)` 可以整個換掉。
- 新的測試檔自帶保險：把 `socket.socket.bind`／`listen` 換成「一叫就失敗」，誰不小心真的綁了埠測試就紅。
- 時間用假時鐘（`Runtime.use_fakes`）；閒置提醒與自動關用 `loop.tick()` 推。
- 共用元件用 node 跑單元測試（跟 `tests/js/` 現有四個一樣：不開瀏覽器、不開埠）。
- 工具庫那邊用 SYNOX 提供的 `synox.web.apps.testing.AppClient`（假瀏覽器：記 cookie、帶 CSRF）直接打 `handle`。
- **真的瀏覽器、真的埠**：只在擁有者帶去的別台電腦做，清單在計畫第 9 節。在那之前，這份 ADR 裡標「待實測」的都不能當成已經成立。

## 8. 推出順序

1. 工作包 0（主機台加固）可以先單獨合，跟功能無關、只有變嚴。
2. 核心（宣告與檢查 → 執行 → 共用元件 → 主機台畫面 → Telegram → SDK）。
3. **記帳**（擁有者舉的例子；資料最像「一本帳」，讀寫都有）。
4. 待辦（最單純的增修刪，驗證共用元件夠不夠用）→ 行事曆（月曆格）→ 子彈筆記 → 筆記。
5. 接外部服務的四個不做 app：它們的畫面在對方的網站。

## 擋不住的（照實寫在 security.md）

- **惡意的畫面程式把你的資料帶走**：它可以把整頁導去外站、把資料夾在網址裡。瀏覽器沒有標頭能擋「導頁」。所以畫面程式跟 `pack.py` 同一級——裝之前報告會明講，第一版也只有官方工具庫有 app。
- **這台電腦上的其他程式與其他使用者帳號**連得到 `127.0.0.1` 的埠。沒有登入拿不到資料；但個人版「直接開網址就進」開著時，同一台電腦的另一個 Windows 帳號開那個網址就進得去——**主機台 8830 現在就是這樣**（`web.local_auto_login`，docs/debug-notes.md）。共用電腦請關掉它，或不用時把服務關掉。
- **假 cookie 的另一半**：如果攻擊者自己有一個有效的 SYNOX 帳號（只可能在伺服器版），惡意畫面可以讓你的主機台悄悄變成登入他的帳號。伺服器版第三方的 python 工具本來就只有擁有者看得到，所以實際上要擁有者自己裝了惡意工具才會發生。
- **瀏覽器外掛**看得到頁面內容；跟任何網頁一樣。

## 不做（這一輪）

- 從別台裝置（手機、區網）開 app；經反向代理轉發 app 的埠。
- kind=cli／mcp 的工具附 app（之後可以把動作對到 `cli.commands`，那邊的危險程度本來就寫在宣告裡）。
- 容器版開放（預設關）；`*.localhost` 主機名；匯出檔案（CSV 下載）；背景即時更新（WebSocket／輪詢）。
- 改 `web.panel`、改教學頁（三份教學之後再補「工具服務」一節）。

## 這份 ADR 沒有驗證的事

- **任何瀏覽器行為**：同站不同埠的請求實際帶哪些 cookie 與 `Sec-Fetch-Site` 值、`Origin: null` 出現的時機、`noopener`／COOP 的效果、CSP 在各瀏覽器的細節。開發機不能開埠，全部是照規格與 0022 研究寫的。
- `*.localhost` 在擁有者用的瀏覽器上會不會解析到本機。
- Windows 上同一個程序開多個 `_Server` 的實際行為（獨佔綁定、關閉時埠多快釋放）。
- 這份文件裡標「提案值」的數字。
