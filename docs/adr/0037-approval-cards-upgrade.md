# ADR 0037：核准卡升級——卡上有檢查與「之前 → 之後」、一張卡好幾個動作、編號與清單、AI 收回自己的卡、過期明說

- 狀態：**提案（契約定稿，還沒有程式）**。分支 `docs/core-unification-adr`。分兩個階段做（下面「階段」欄）。
- 基準：分支 `dev`，commit `86a930d`。文中的 `檔案:行號` 都是這個 commit 的。
- 來源：合一規劃（維護者的私有文件庫，2026-11-17）第 4.2 節、第 11.9 節。對應 [QuestionToUser.md](../QuestionToUser.md) 的 Q2（卡要不要編號、能不能列出還開著的）。
- 相關：[0035](0035-workmode-core.md)（批次方案的卡的內容從哪來）、[0038](0038-wake-ai-after-card.md)（按了之後叫醒 AI）、
  [0025](0025-guard-core-and-stepup.md)（按 ✅ 以人的身分再檢查、驗證碼不經過 AI——不變）。
- 程式：`src/synox/agent/approve.py`、`agent/loop.py`（出卡之後這一輪怎麼走）、`agent/claims.py`（卡上的動作不算做完）、新的系統群組 `card`。
- 測試：`tests/test_approve_cards.py`；既有的 `tests/test_agent*.py` 裡關於卡的測試不可以壞。

## 背景

SYNOX 現在的卡（**已查證** `src/synox/agent/approve.py`）：一個動作一張、卡上是指令＋一句說明、10 分鐘、過期就是按不動、
按了之後只在 AI 的記憶裡記一句、沒有編號、重開就全部作廢。它做對而且**不改**的：按的人要是本人、卡一律私訊、
按 ✅ 以人的身分再 authorize 一次、驗證碼不經過 AI、Telegram／Discord／網頁都能按。

先前的聊天機器人的卡比較強的六樣，這份補進來。

## 決定

| # | 加什麼 | 決定 | 階段 |
|---|---|---|---|
| 1 | 卡上的檢查與「之前 → 之後」 | 批次方案（`agent.work` 的 `apply`）的卡：內容來自工具的 `show`，最上面是系統寫的 ⚠。其他的卡照舊（指令＋說明；工具自己要求確認的用它給的 `summary`） | 2 |
| 2 | 期限 | 一般的卡照舊 10 分鐘。批次方案的卡到方案過期為止（最長 `plan_ttl_hours`，預設 12 小時）。**過期都要明說** | 2（批次）、4（全部） |
| 3 | 執行完叫醒 AI | [0038](0038-wake-ai-after-card.md) | 1 |
| 4 | 一張卡好幾個動作 | 同一輪第 2 個要卡的動作併進同一張（卡原地改寫）；整張一起核准或取消 | 4 |
| 5 | 編號、列出還開著的卡 | 每張卡有 `#編號`；`/card` 列出、`/card <編號>` 重送 | 4 |
| 6 | AI 收回自己的卡 | 系統工具 `card__void(id, reason)`，只動自己發的卡 | 4 |
| 7 | 重開之後 | 卡照舊全部作廢（這一輪不做持久化）；但批次方案會在下一輪說「卡作廢了，要再開嗎」（[0035](0035-workmode-core.md)） | 2 |

## 1. 卡的資料

`approve.py` 的 `Cards`（包著 SDK 的 `Pending`）裡，每張卡的 payload 從一個動作變成：

```python
@dataclass
class CardItem:
    path: str                         # 要執行的節點
    argv: list[str]                   # 或 run／rerun（schema 模式、工具自己要求確認；照舊）
    shown: str                        # 卡上那一行：「/note_clear」
    why: str = ""                     # 一句說明（節點的 summary 或工具給的 summary）
    grant: str = ""; rerun: Callable | None = None; run: Callable | None = None

@dataclass
class Card:
    id: int                           # #編號：每個人自己的流水號
    token: str                        # 按鈕背後的隨機字串（Pending）
    owner: int; chat_id: int; thread: str | None
    kind: str                         # "action"｜"work_apply"｜"tool_confirm"｜"habit"
    source: str                       # "ai"｜"human"｜"tool"（誰引起的）
    items: list[CardItem]
    top: list[str]                    # 最上面由系統寫的幾行（⚠）
    body: list[str]                   # 「之前 → 之後」那幾行（work_apply）
    created: float; expires: float
    message_id: int | None            # 卡片那一則（改寫用）
    turn: str = ""                    # 哪一輪開的（併卡只併同一輪的）
    work: str = ""                    # work_apply：WorkSpec.key；plan_id 在 items[0].argv
```

`ApprovalDesk.request()` 既有的參數都留著，多幾個可選的（舊的呼叫不用改）：

```python
def request(self, api, chat_id, user, node, argv, why="", *, grant="", rerun=None, header="⚠️ AI 想執行",
            lines=None, run=None,
            kind="action", source="ai", top=None, body=None, ttl=None, work="") -> Card
```

- 回傳從 `None` 改成那張 `Card`（呼叫端要編號）。
- `ttl=None`＝`app.timing.confirm_ttl`（10 分鐘）。
- 編號：每個人自己的流水號，**只有下一個號碼**存檔（`data/agent_cards.json`：`{"next": {"<使用者>": 13}}`，jsonstore）；卡本身不存檔。
  這樣重開之後不會又從 #1 開始，跟畫面上還留著的舊卡撞號。

## 2. 卡片長什麼樣

固定的順序（每一段沒有就省略）：

```
⚠️ AI 想執行　#12
⚠ 這次放寬了：課後 90 分鐘內不排 → 30 分鐘            ← top：系統寫的
⚠ 挑錯者指出、還沒解決：11/22（六）：下午的課之後馬上接了東西
把沒看完的 6 部往後排（11/20–11/28）                   ← 批次方案：show 的 summary
• 學A觀念（第 3 部）　11/20（四）20:00–21:30 → 11/22（六）09:00–10:30   ← body：之前 → 之後
• …
（今天 23:40 前有效；按 ✅ 才會執行）
[✅ 執行] [❌ 取消]
```

- 一般的卡（`kind="action"`）照現在的樣子，只在標題多 `#編號`：`⚠️ AI 想執行　#12：/note_clear`、說明、參數、期限。
- `body` 最多 30 行（Telegram 一則的長度）：超過＝前 29 行＋「…另有 N 筆（網頁可以看全部）」。網頁的卡不截。
- 期限的寫法：10 分鐘以內寫「N 分鐘內有效」；超過 1 小時寫**絕對時間**（「今天 23:40 前有效」「明天 09:15 前有效」）。
- 所有來自工具或 AI 的字照通道跳脫；`top` 與期限那一行只由系統的樣板產生。

## 3. 批次方案的卡（`kind="work_apply"`，階段 2）

AI 叫了 `apply`、[0035](0035-workmode-core.md) 的閘門都過了之後，由 `workhost` 開：

| 欄位 | 來源 |
|---|---|
| `top` | `workmode.card_head()`（放寬的、排不進去的、挑錯者的、沒有挑錯的） |
| 摘要 | `show` 的 `summary` |
| `body` | `show` 的 `changes[]`：每筆一行 `• {show.title}　{show.before} → {show.after}`；`add`＝`• ＋ {title}　{after}`；`delete`＝`• － {title}　{before}` |
| `ttl` | `plan_expires - now`（已經過期就不開卡，回 AI G3 的字） |

按 ✅ 之後（順序固定）：

1. 以按的人的身分對**工具的 `apply` 指令** authorize（via=BUTTON）。沒解鎖＝卡留著、請他先解鎖再按一次（照舊，ADR 0025 §5.4）。
2. 核心叫一次 `show`：`fresh` 是 `false` 或 `state` 不是 `open`＝不執行，卡改寫成「資料在你看卡之後變了，沒有套用」，叫醒 AI（它會回到查詢）。
3. 執行 `apply`。工具自己還會再比一次 `fingerprint`（[0033](0033-work-protocol-work1.md) 規則 2）。
4. 成功＝核心叫 `verify` → `workmode.report()` → 結果訊息（含「↩ 整批退回」）→ 叫醒 AI。
5. 失敗＝結果訊息照 `report()` 的字 → 叫醒 AI。

批次方案的卡**不併卡**（一份方案一張）。出了這張卡，AI 那一輪就結束（跟現在一樣）。

### 按鈕綁在哪（**已查證**的限制）

SDK 對「綁在危險節點上的按鈕」有一條自己的規則：訊息超過 `button_ttl`（預設 30 分鐘）就按不動
（`vendor/isdtelekit/core/dispatcher.py:298`；vendor 不能改）。現在的卡綁在 `agent.ai_approve`（DANGER），10 分鐘的卡不受影響；
但 12 小時的卡會在第 30 分鐘被 SDK 擋掉。

所以批次方案的卡用**另一個前綴、另一個節點**：`registry.bind_callback("agent_plan:", "agent.plan_approve", …)`，
`agent.plan_approve` 的 effect 是 WRITE（不是 DANGER、不是 🔐）、不給 AI、不在 `/help`。它不是放寬：

| 30 分鐘那條規則要防的 | 這張卡用什麼防 |
|---|---|
| 很久以前的危險按鈕還按得動 | 卡自己的期限（方案的 `expires`，寫在卡上）；token 過期就沒了 |
| 按的時候情況已經變了 | 按 ✅ 那一下的 `fresh` 檢查＋工具自己的 `fingerprint` 檢查 |
| 不是本人按的 | 卡有主人；按 ✅ 以人的身分對**真正要執行的那個 DANGER 指令**再 authorize（含解鎖） |
| 重開之後的舊按鈕 | token 只在記憶體，重開就沒了 |

「↩ 整批退回」（30 分鐘）照舊可以綁在 DANGER 的 `work.revert` 上。

## 4. 一張卡好幾個動作（階段 4）

現在 AI 那一輪在第一張卡就結束（`loop.py:691`）。用文字協定的來源一次只叫一個工具，所以要併卡就得讓這一輪走下去：

1. 出了卡之後這一輪**不結束**。那次工具呼叫回給 AI 的字：
   「（已放進確認卡 #12，**還沒執行**。同一批要確認的動作可以繼續放進來；跟它有先後關係的動作不要現在做。最後請告訴使用者去按卡。）」
2. 同一輪後來又有要卡的動作＝**併進同一張**（條件全部成立才併，否則另開一張）：同一個主人、同一個聊天與對話、同一輪（`turn`）、
   那張卡還開著、`kind` 都是 `action`、`source` 都是 `ai`、兩邊都不是要驗證碼欄位的指令、併完不超過 `CARD_ITEMS_MAX = 12`（提案值）。
   併的時候卡片**原地改寫**（多一行動作）；期限不延長。
3. **卡開著的時候，這一輪不再直接寫入**：同一輪後面的 WRITE 呼叫（不用卡的那種）回「有卡在等使用者按，先讓他按完；這個動作等他按了再做。」（`ok=False`）。
   READ 照常。這是為了不讓「卡上的刪除」與「馬上執行的新增」的先後順序亂掉。
4. 這一輪結束時，系統在 AI 的回覆後面加固定的一行：「🔒 有 N 個動作在確認卡 #12 上，等你按。」
5. **卡上的動作不算做完**（`claims.py`）：`Evidence.carded` 是真的那幾筆不再當成「這一輪真的寫入了」的證據。
   回覆說「已經刪了」而證據只有卡上的＝`REJECT`，修正字句「那個動作在確認卡上，還沒執行；改成請使用者去按卡。」

按鈕：`[✅ 全部執行] [❌ 全部取消]`（只有一個動作時照舊是「執行／取消」）。按 ✅：

- **每一個動作**各自以按的人的身分 authorize（via=BUTTON）。有任何一個不通過＝整張不執行、說是哪一個、為什麼。
- 照卡上的順序一個一個執行。第 k 個失敗＝停，結果訊息寫「第 k 個失敗：…；後面 N 個沒有執行；前面 k−1 個已經做了」。
  **不自動還原**（要整批還原的事請走批次方案，那是 [0033](0033-work-protocol-work1.md) 的 `apply`）。
- 叫醒 AI 一次，帶每個動作的結果（[0038](0038-wake-ai-after-card.md)）。

不併的：批次方案的卡、工具執行到一半要求確認的卡（`tool_confirm`）、習慣提議的卡（`habit`）、人自己打指令引起的卡。

## 5. 編號、清單、收回（階段 4）

系統群組 `card`（跟提醒、排程同一種登記）：

| 指令 | 誰能用 | 做什麼 |
|---|---|---|
| `/card` | 人（不給 AI） | 列出我還開著的卡：`#12　2 個動作　還有 7 分鐘`、`#13　排程／重排　今天 23:40 前` |
| `/card <編號>` | 人（不給 AI） | 把那張卡**重送一次**（舊那一則的按鈕拿掉、改寫成「↻ 這張卡重送到下面了」）。內容、期限不變 |
| `/card_void <編號> [原因]` | 人；AI（工具名 `card__void`，WRITE） | 收回一張卡：改寫成「🚫 收回了這張卡：{原因}（沒有執行）」、拿掉按鈕 |

`card__void` 給 AI 時的限制（在 handler 裡看來源，不是權限——權限仍然只有 `policy.decide`）：

- 只能收回**自己發的**（`source="ai"`）、這個人的、這段對話的卡。別的回「沒有這張卡」。
- `reason` 必填：一行、120 字內、清掉控制字元。卡上寫「🚫 AI 收回了這張卡：{reason}」。
- 「換掉」＝先 `card__void` 再照常提出新的動作；沒有另外的「換卡」工具。
- 收回不叫醒 AI（它自己做的）。批次方案的卡被收回＝`workmode.card_event("voided")`。

AI 怎麼知道編號：出卡時回給它的那句話裡有 `#12`；另外每一輪第 7 層多一行狀態「[還開著的確認卡：#12、#13]」（沒有就不放）。

## 6. 過期

- 批次方案的卡（階段 2）、其他的卡（階段 4）：到期時由常駐迴圈的一個任務（`system.cards`，每 30 秒看一次；沒有 runtime 時在下一次有人按或下一輪開頭檢查）
  把卡片**改寫**成「⌛ 過期了，沒有執行」、拿掉按鈕，並叫醒 AI 一次（內容是「沒有執行（過期）」，[0038](0038-wake-ai-after-card.md)）。
- 改寫失敗（訊息太舊、通道不支援改寫）＝另送一則同樣的字。改寫要檢查回傳值，不能只包 try／except。
- 過期之後有人按：照舊回「⌛ 這張確認卡過期了」。

## 不改的

按的人要是本人（別人按＝「這不是你的按鈕」，卡不作廢）；卡一律私訊給下令的人；按 ✅ 以人的身分再 authorize 一次；
沒解鎖就先解鎖、卡留著；驗證碼永遠不經過 AI；工具自己要求確認（`needs_confirm`）的來回；Discord 與網頁的畫法；頻道 AI 不出卡。

## 不做的事

- **卡的持久化**（重開之後卡還在）：這一輪不做。
- **部分核准**（一張卡只勾其中幾個）：不做，整張一起。
- **併卡之後自動還原**：不做。
- **AI 自己核准、AI 延長期限**：永遠不做。
- **用模型產生卡上的字**：不做；卡上的字只有樣板、工具的 `show`／`summary`、清理過的挑錯者欄位。
- **把一般的卡的期限拉長**：不做（短比較安全）。

## 測試怎麼寫

`tests/test_approve_cards.py`（SDK 的 `BotHarness`、`FakeAdapter`、假時鐘；不開任何通道）：

階段 2：

1. 既有行為：一般的卡多了 `#編號`，其他字不變；`request()` 的舊呼叫方式照樣能用、回傳 `Card`。
2. 編號每個人各自遞增；重新 `app.build`（模擬重開）之後接著往下編。
3. 批次方案的卡：`top` 在最上面、`body` 是 `show` 的字、31 筆時只列 29 行＋「另有 2 筆」、期限寫絕對時間。
4. 批次方案的卡 31 分鐘之後按 ✅：**按得動**（綁在 `agent.plan_approve`）；一般的卡 11 分鐘之後按＝過期。
5. 按 ✅ 時 `show.fresh` 是 `false`：不執行、卡改寫、AI 被叫醒。
6. 按 ✅：對工具的 `apply` 指令做了 authorize（把那個人降成沒有權限的角色＝不執行、說原因）。
7. 開著驗證器保護、還沒解鎖：卡留著、請他解鎖；解鎖後同一張卡按得動。
8. 別人按：回「這不是你的按鈕」、卡還在、按鈕還在。
9. 過期：卡被改寫成「⌛ 過期了，沒有執行」、AI 被叫醒一次、之後按＝過期的字。改寫回 `{"ok": false}` 時另送一則。
10. 重開：舊卡按了＝過期的字；批次方案的狀態回到 `check`（[0035](0035-workmode-core.md) 的測試）。

階段 4：

11. 同一輪兩個危險動作：只有一張卡、兩行動作、卡片是原地改寫的（同一個 `message_id`）；按 ✅ 兩個都執行、順序對。
12. 併卡的條件各壞一個＝另開一張：不同輪、第一張已經按了、其中一個要驗證碼、超過 12 個、其中一個是批次方案。
13. 卡開著時同一輪的 WRITE 被擋（回的字對）、READ 照常。
14. 回覆後面有「🔒 有 N 個動作在確認卡 #12 上」；AI 說「已經刪了」＝被完成宣稱的閘門擋下。
15. 兩個動作、第 2 個 authorize 不過：整張不執行。第 2 個執行失敗：第 1 個做了、結果訊息三件事都寫了、沒有還原。
16. `/card`：只列自己的、還開著的；`/card 12` 重送後舊那一則的按鈕不見；AI 的工具清單裡只有 `card__void`，沒有列清單、重送的工具。
17. `card__void`：收回自己發的＝卡改寫、按了沒反應；收回別人的、人引起的、別段對話的＝「沒有這張卡」；沒給原因＝第 4 關擋。
18. 第 7 層有「還開著的確認卡」那一行；沒有卡時沒有那一行。
19. 頻道 AI：照舊不出卡。網頁：卡在那一段對話裡、按鈕要真的在那則訊息上（invariant 9）。

## 跟規劃不一樣的地方

| 規劃 | 這份 | 為什麼 |
|---|---|---|
| 批次方案的卡 12 小時 | 另外綁一個不是 DANGER 的節點 | SDK 對危險節點的按鈕有 30 分鐘的上限，vendor 不能改（**已查證**）。不這樣做，12 小時的卡在第 30 分鐘就按不動 |
