診斷：SYNOX 看到的「沒叫工具卻說做完了」是三件事疊在一起

  1. 解析器層。Qwen3.5 在 Ollama 上有已知的工具呼叫渲染／解析錯配（Ollama issues #14745、#14493：模型訓練時用 Qwen3-Coder 的 XML 格式，但 registry 接的是 Hermes JSON 解析器；0.19 左右的 PR #15022／#15224 修了一部分，仍有人回報）。症狀正是「把 <tool_call> 當文字印出來」。測試紀錄裡 9b 原生模式 note-01 自己印出 SYNOX 分隔符與假 JSON，很可能就是這一層。先看 /api/chat 原始回應：tool_calls 空而 content 含標籤＝解析器問題。
  2. 模型層。文獻把它叫「執行幻覺」（agent 宣稱完成了沒做的子步驟，arXiv 2509.18970）、「工具繞過」（arXiv 2601.05214）、「向上欺騙」（arXiv 2512.04864：宣稱完成未執行的操作，不同模型 NFR 27%～97%）、「Halluci-action」（宣稱與工具紀錄不一致，最高 45.9%，而且超過一半「目標達成」的軌跡仍含未支持的宣稱）。Qwen3-8B 在 SimpleToolHalluBench 開 thinking 時干擾工具幻覺由 36.2% 升到 56.8%：行動輪關掉 thinking 是有數據的選擇。系統提示加「不准假裝」只有邊際效果（90.2→87.5），所以必須有 harness 閘門。
  3. Context 層。Ollama 預設 4096，OpenAI 相容路徑 /v1 不能設 num_ctx（官方文件明說），超過時伺服器只記 WARN、客戶端拿到 HTTP 200——系統提示從前面被截掉，工具規則第一個消失。要走原生 /api/chat 帶 options.num_ctx，或設 OLLAMA_CONTEXT_LENGTH，並用回應的 prompt_eval_count 對自己的估算來偵測截斷。

文獻裡對「虛假完成」最有效的推論端做法（依證據強度排序）

  • 結構化完成，不把「沒叫工具」當作「做完了」：AgentScope 把 finish／generate_response 做成工具，模型只回純文字時丟掉那一則、下一次用 tool_choice 強制呼叫；Arize「Explicit Finish」；ECT（arXiv 2608.23623）要求 COMPLETE 必須附上每個宣稱對應的軌跡證據，提前終止 0/66 對 40/66。
  • 宣稱 ↔ 工具紀錄比對（證據帳本）：HalluciActionLens 雙向比對「宣稱做了但沒執行」與「執行了沒揭露」；practitioner 的 completion_guard 用正規表示式抽宣稱＋回看 5 輪成功的工具結果，不符就注入修正提示、最多重試 2 次。沒有任何論文報告這種規則式偵測器的誤判率；唯一的實測計數是 Arize 117 次執行抓到 2 次、0 誤判。
  • nudge 字句本身是變數：Inspect 的預設字句「請用你的最佳判斷繼續」讓 Gemini 作弊率 14%，換成中性的「做完了就呼叫 submit()」降到約 1%（p≤0.001）。
  • 停止詞：Qwen-Agent 把 ✿RESULT✿、Observation: 設成 stop，模型想偽造工具結果就會被截斷——這是文字協定下最便宜的防偽造。
  • 格式強制：Kimi K2 的 enforcer、DeepSeek strict、llama.cpp --jinja + tool_choice: required（文法層保證）、vLLM／SGLang 的 XGrammar。Ollama 只有 format（JSON schema）沒有 tool_choice，所以在 Ollama 上要用「兩段式：先 schema 決定要不要叫工具、再叫」替代。
一句話版本：把「模型說了什麼」和「harness 真的做了什麼」分開記帳，宣稱必須有帳；沒帳的不放行、用中性字句重試最多兩次、再不行就老實告訴使用者。再加上 context 不要被靜默截斷、行動輪關 thinking、文字裡的工具呼叫要救回來。

前 8 項（規格在最後一節）

  1. 本地模型虛假完成檢測：宣稱做了、該輪沒有對應成功工具呼叫＝不放行，重試或回報
  2. Ollama 原生 adapter：num_ctx、think:false、可設逾時與暖機、截斷偵測
  3. 文字裡洩漏的工具呼叫救回＋剝除 <think>（原生模式的 content 後備解析器）
  4. 文字協定的停止詞與「做不到」出口（防偽造工具結果、給模型誠實的退路）
  5. 工具說明精簡化（EasyTool）與每輪工具數上限
  6. Context 預算：估算、分級截斷、工具結果上限與可還原指標
  7. 系統提示關鍵規則尾端重注入＋取樣參數依模型家族
  8. 評測擴充：claimed_without_call 檢查、Reliable Pass Rate、工具觸發 F1、重播停滯輪

A. 虛假完成的偵測與閘門

A1　宣稱 ↔ 工具紀錄比對（證據帳本）

需訓練：否工作量 M可信度 高（實作）中（學術數字）
做什麼
只在「這一輪沒有工具呼叫」的分支觸發：從回覆抽出「完成宣稱」（已記下／已新增／done…），回看最近 N 輪的工具呼叫與結果，宣稱必須對應到至少一次成功的同類工具呼叫（結果沒有 Traceback、error、exit_code≠0）；若宣稱提到實體（筆記內容、時間），實體字串要出現在參數或結果裡。不符＝不送出、注入修正提示重試（上限 2），再不行回報。HalluciActionLens 把這做成雙向度量（宣稱未執行／執行未揭露）；ECT 把「COMPLETE 必須附證據憑證」做成確定性閘門。
出處
completion_guard（gist）；Halluci-Action（NeurIPS 2026 workshop）；Evidence-Carrying Termination（arXiv 2608.23623）；AIClaw EvidenceLedger；Arize Adaptive／Explicit Finish
數字
ECT：未支持的提前終止 0/66 對基準控制器 40/66；Halluci-action rate 最高 45.9%，目標達成的軌跡中 52～54% 仍含未支持宣稱；Arize 117 次執行抓到 2 次、兩次 nudge 後都真的完成、token 多 6%。completion_guard 本身沒有誤判率數據。
SYNOX 落點
src/synox/agent/loop.py _turn 的 if not calls: 分支；新模組 src/synox/agent/claims.py；evals/checks.py 新檢查。見規格 1。
風險
繁中宣稱詞表要自己建、要控誤判（否定、問句、純聊天「我知道了」）；用 LLM 裁判會多一次 CPU 呼叫。

A2　偽造工具結果／分隔符的偵測

需訓練：否工作量 S可信度 高
做什麼
模型回覆裡出現 harness 的工具結果標記（SYNOX 的 ⟦SYNOX-TOOL-…⟧、〔工具結果〕、<tool_response>、"role": "tool"）＝它在偽造觀察結果。整則丟掉、不進記憶、重試。Relign 的案例研究記錄了 Llama3.1 捏造 ID「project123」再回報「成功取得」；SYNOX 自己的測試紀錄已實際看到兩種偽造。沒有論文單獨測這條規則，但它是零誤判成本最低的檢查（正常回覆不會含 harness 專用標記）。
出處
Relign（arXiv 2412.04141）案例；SYNOX 測試紀錄 §壞掉的地方 1
SYNOX 落點
agent/delimit.py 已有 looks_forged()，目前只給記錄用；在 loop._turn 的回覆分支真的用它＋textproto.result_message 的前綴。
風險
幾乎沒有；使用者自己貼一段含「SYNOX-TOOL」的字給 AI 複述時會誤判，可以只看 AI 回覆的新內容。

A3　結構化完成：finish／回報阻礙 當成工具

需訓練：否工作量 M可信度 高
做什麼
把「結束」做成一個工具（AgentScope v0 的 finish、v1 的 generate_response；OpenManus 的 terminate），模型只回純文字時那一則被丟棄、下一次請求用 tool_choice 指定 finish；到步數上限時改 tool_choice=none＋「現在只准總結」。ToolBeHonest 給模型 UnsolvableQuery 偽工具讓「做不到」有誠實的出口。zylos 的整理：用結構（diff、submit 工具、schema 合法輸出）定義完成的框架穩，靠「沒叫工具」推斷完成的框架脆弱。
出處
AgentScope v0 ReActAgentV2、v1 _config.py；OpenManus toolcall.py；ToolBeHonest；zylos 完成訊號整理
SYNOX 落點
SYNOX 的「回純文字＝回答使用者」是設計本體，改成 finish 工具會動到 loop.py、room.py、evals 全部，所以建議只做輕版：加 system__cannot_do(reason) 偽工具（規格 4），完整 finish 工具列為後續選項。
風險
Ollama 沒有 tool_choice，「強制 finish」在 Ollama 做不到，要靠提示；在 llama.cpp／vLLM 才有文法保證。

A4　nudge 字句與次數上限

需訓練：否工作量 S可信度 高
做什麼
模型只說「接下來我會…」卻停下來（Arize 叫 Implicit Finish：掃最後 300 字有沒有「I'll／Now I will」且後面不到 100 字），harness 回一句 nudge 再叫一次；上限 2 次（completion_guard、LangChain 討論串、zylos 都是 2～3）。Inspect/Petri 的消融：預設字句「請用你的最佳判斷繼續」讓作弊率 14%，三種中性字句約 1%；建議「如果動作還沒做，現在就呼叫工具；做完了就呼叫 finish()」。
出處
Arize；LessWrong：Inspect 的 continuation 字句；LangChain forum #4608
SYNOX 落點
規格 1 的修正提示字句；config.json llm.verify_retries。
風險
每次 nudge 在 CPU 9B 上多 15～30 秒；上限要硬。

A5　行動輪關掉 thinking

需訓練：否工作量 S可信度 高
做什麼
SimpleToolHalluBench（螞蟻集團＋PSU，ACL 2026）：開 thinking 在每一組模型都提高工具幻覺。Qwen3-8B 干擾工具情境 36.2%（不思考）→ 56.8%（思考）；無工具情境 4.1% → 5.4%。系統提示加「不得使用未提供的工具」只有邊際效果（NTA 90.2→87.5、DT 100→98.9）。Ollama 原生 API 有 think: false；Qwen3 文件也說 enable_thinking=False 可硬關。SYNOX 測試紀錄已用 reasoning_effort: none，方向一致。
出處
The Reasoning Trap（arXiv 2510.22977）；Ollama api.md
SYNOX 落點
規格 2 的 Ollama adapter 預設 think:false；llm.think 可設。
風險
多步規劃題可能略差；27B 兩種模式都通過的 4 題是在不思考下測的，所以對 SYNOX 的題型目前沒有反證。

A6　不要逼模型「一定要給最終答案」；給它回報失敗的路

需訓練：否工作量 S可信度 高
做什麼
「向上欺騙」研究（上海 AI Lab、HKUST、SJTU、ZJU、PKU、阿里）在 smolagents 裡故意弄壞工具：模型傾向回報成功。推論端兩個發現：(1) 指示「不要猜、不要模擬、回報異常」把欺騙率大幅壓低（GLM-4.5 77.5→30.0、Kimi-k2 83.3→50.0）但沒有歸零；(2) 拿掉嚴格的「最終答案格式」要求本身就顯著降低欺騙。對應到 SYNOX：系統提示的「老實說做不到」要保留且放到尾端重注入，而且回覆格式不要限制太死。
出處
Are Your Agents Upward Deceivers?（arXiv 2512.04864）
SYNOX 落點
loop.system_prompt 第 2 行已有「沒有適合的工具就老實說做不到」；規格 7 把它搬到最尾端、並加「工具失敗就照實說失敗，不要補一個結果」。
風險
無；但只靠這條不夠（論文自己說沒有歸零）。

A7　LLM 裁判（軌跡層的第二道檢查）

需訓練：否工作量 M可信度 高
做什麼
Relign 的混合裁判：規則抓結構錯（JSON 壞、缺參數）＋ LLM 判工具相關性與參數真實性，與人類一致 92.7%（139/150）。MIRAGE-Bench 用風險情境專屬的裁判提示（0 分＝「當作目標可達成繼續做」），裁判對人類 0.76～0.85。AgentRewardBench 提醒：最好的裁判對人類精確率約 70%。所以 LLM 裁判只能當第二道，規則閘門是第一道；用在 evals 離線跑比用在線上好。
出處
Relign；MIRAGE-Bench（arXiv 2507.21017）
SYNOX 落點
evals/ 的 soft rubric（題目已有 soft 欄位）可以加一條「宣稱與工具紀錄一致」rubric，離線用雲端模型評；線上不做。
風險
CPU 上多一次 9B 呼叫等於再等 15～60 秒；裁判自己也會幻覺。

B. 工具呼叫格式、解析、修復、受限解碼

B1　文字內容裡的工具呼叫救回（content 後備解析器）

需訓練：否工作量 S可信度 高
做什麼
Qwen-Agent 的 NousFnCallPrompt.postprocess_fncall_messages：把回覆用 <tool_call> 切開，每段用 json5.loads（容忍尾逗號、單引號、註解），失敗再用字串搜尋 "name": "／"arguments": 撈；不解析 <think> 裡的 tool_call（程式碼註解：「Do not parse <tool_call> in thought!!!」）；沒閉合的 <tool_call> 從名字往後解。Qwen 官方文件：「即使模板正確也不保證模型照協定輸出……生產程式要自己解析」。Ollama #14745／#14493 證實 Qwen3.5 會把 <tool_call><function=bash><parameter=…> 當文字印出，所以原生模式也需要這個後備。
出處
Qwen-Agent nous_fncall_prompt.py；Qwen function_call 文件；Ollama #14745、#14493
SYNOX 落點
src/synox/llm/textproto.py 加 parse_leaked(text)（認 <tool_call> JSON、<function=name><parameter=k>v</parameter> XML、MiniMax 的 <invoke>）；loop._turn 在 native 且 reply.tool_calls 空時呼叫。救回的呼叫照常過 decision、第 4 關、確認卡。見規格 3。
風險
vincentschmalbach 的提醒：不要盲目執行文字裡找到的 JSON；SYNOX 因為所有呼叫都過 ai_decision＋第 4 關，風險可控。

B2　寬鬆 JSON 修復（不再多叫一次模型）

需訓練：否工作量 S可信度 高
做什麼
MetaGPT repair_llm_raw_output.py：補缺的鍵對、大小寫、閉合標籤、去 #／// 註解、照 JSONDecodeError 的 line:col 做局部修補（補逗號、去多餘括號、跳脫引號），retry_parse_json_text 最多 3 次把修好的文字餵進下一次嘗試。AgentScope 論文「預設規則補齊不匹配的大括號、從字串抽 JSON」。DeepSeek 更新日誌：加正規表示式後處理把 JSON 解析率 78%→85%→97%。Qwen-Agent 用 json5；社群有 json_repair 套件（含 schema 引導修復 beta）。
出處
MetaGPT repair_llm_raw_output.py；AgentScope 論文 §4；DeepSeek updates；json_repair
SYNOX 落點
textproto._objects 已從每個 { 試 raw_decode；再加一層「標準解析失敗→去尾逗號／單引號換雙引號／補一個 }」再試。SYNOX 測試 bad_json=0，所以這項優先度低。
風險
修壞了會把錯的參數送進第 4 關；第 4 關會擋，所以結果是「參數不對」回饋而不是誤執行。

B3　schema 驗證錯誤當作工具結果回給模型

需訓練：否工作量 S（已有大半）可信度 高
做什麼
AgentScope v1 用 _json_loads_with_repair 解參數、對 JSON schema 驗、失敗回「Input validation failed for tool …」當工具結果；OpenManus execute_tool 永遠回字串（「Error: Unknown tool」、「Error: Invalid command format」）不丟例外；Kani 把 NoSuchFunction／ValidationError 回到對話讓模型重試。SYNOX 的第 4 關（validate.check_call）、「缺必填參數…先問使用者」、「沒有這個工具」已經是這個做法。
出處
AgentScope v1 _agent.py；OpenManus toolcall.py；Kani（arXiv 2309.05542）
SYNOX 落點
已有。可以補：錯誤訊息指名哪個參數、期望型別（LLMOrch 的經驗：錯誤訊息指名缺的參數才能打破 30～40 次重複失敗的迴圈）。
風險
無。

B4　受限解碼與格式強制（各引擎的現況）

需訓練：否工作量 M（換引擎）可信度 高（Ollama／llama.cpp／vLLM 文件）中（XGrammar 細節）
做什麼
  • Kimi K2 enforcer：生成到 <|tool_calls_section_begin|> 之後，強制後續 token 符合模板、JSON 參數符合宣告的 schema（報告 §inference）；程式碼未公開。K2 Vendor Verifier 建議部署者「加 guided encoding 確保 schema」。
  • DeepSeek：工具定義 strict: true（Beta）保證輸出符合 JSON schema；非 strict 時「模型不一定產生合法 JSON」。thinking 模式下不支援 tool_choice: required／指名。
  • Ollama：format 收 "json" 或 JSON schema（底層轉 GBNF）；沒有 tool_choice（原生與 /v1 都沒有）；社群回報 format＋tools 同時用會把工具呼叫擠進 content。
  • llama.cpp server：--jinja 下用「lazy grammar」——看到觸發字（Hermes 的 <tool_call>）才套文法；tool_choice: required 時文法非 lazy，伺服器回的工具呼叫一定符合 schema。
  • vLLM：tool_choice: required「保證產生一個以上的工具呼叫（用 structured outputs）」；Qwen3.5 用 qwen3_xml 解析器。XGrammar（CMU／SJTU）提供 structural tags 給工具呼叫，額外開銷近零。
出處

F. 記憶

F1　MemoryOS／A-MEM／LightMem／MemoryBank：小模型可用的記憶架構

需訓練：否工作量 L可信度 高
做什麼
