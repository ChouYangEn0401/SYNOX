兩台 SYNOX 怎麼安全地互派任務

主控台（console）與哨兵（worker）之間的連線：除了大家 polling 同一個 Telegram 對話、Cloudflare Tunnel、公網 webhook、VPN 之外還有什麼路，哪一條最簡單又最不依賴別人，以及為什麼最後選了「端對端信封 ＋ 可換的傳輸層」。

01 · 題目與限制

擁有者 2026-11-12 的問題，整理成可以打勾的條件：

條件意思
安全只有自己的那幾台看得懂、改得了訊息；別人就算能看到封包、能連上埠，也做不了事。
簡單兩台電腦、一個 config、一次配對。不要架一套伺服器、不要管憑證。
不靠第三方不經 Telegram／Cloudflare／Tailscale 這類別人的服務；自己的內網優先。
不開公網不把任何東西直接掛在公網上等人敲。
雙向、有狀態派任務、回狀態、要求重做、交接給另一台、知道誰在線。
好接 event bus／observer後端收到什麼都變成事件，誰想反應就訂閱，不要寫死在收訊的地方。
之後接 IoT攝影機、Arduino、樹莓派掛得上來，而且不用為它們另外設計一套安全。

現有的 SYNOX 已經有的東西直接沿用：保管箱（Fernet、scrypt）、cryptography 套件（已是相依）、唯一的 authorize()、dispatcher.handle（排程就是這樣觸發指令的）、SDK dispatcher 的 observer 介面。

02 · 關鍵想法：把「安全」跟「走哪條路」分開

一開始列出來的四個選項（Telegram、Cloudflare Tunnel、webhook、VPN）其實都在回答同一個問題：封包怎麼到對面。安全是附帶在那條路上的：Telegram 靠 Telegram、Tunnel 靠 Cloudflare、webhook 靠 TLS 憑證、VPN 靠 VPN。路一換，安全就要重做。

反過來想：如果每一封訊息本身就是加密並簽過名的，那它走哪條路都無所謂。路只要能搬 bytes 就好，可以是區域網路 TCP、一個共用資料夾、MQTT、甚至序列埠或貼進聊天室的一行 base64。路被偷看、被竄改、被重放，信封都驗得出來。這就是 WireGuard、Signal、Syncthing 都在用的分法。

03 · 候選方案比較

先看「路」。每一條都可以配上信封；差別在要不要靠別人、要不要開公網、設定多煩、能不能穿 NAT。

路不靠第三方不開公網埠設定穿 NAT延遲多裝套件評語
Telegram 共用對話（大家 polling）靠 Telegram是低是秒級無bot 之間走不通：Telegram 規定 bot 看不到其他 bot 的訊息（防止互相觸發），兩支 bot 放同一個群組彼此是聾的。要通只能用使用者帳號（MTProto，Telethon 之類），那就不是 bot、也違反 SYNOX 的設計。兩邊共用同一個 token 也不行（同時兩個 getUpdates 會 409）。
Cloudflare Tunnel靠 Cloudflare是中是百毫秒cloudflared好用，但流量經 Cloudflare 邊緣、要有網域與帳號；擁有者明說不想靠外部雲。
公網 webhook（自己架 HTTPS）是要開高要固定 IP／DDNS百毫秒憑證要管憑證、要對外開埠、每次收訊都是公網上任何人都能敲的入口。擁有者明說不想。
VPN：Tailscale／ZeroTier協調伺服器是別人的是低是低客戶端最省事的跨網方案；Headscale 可以自架協調伺服器，但那又多一台要顧的伺服器。
VPN：WireGuard（純）是一端開一個 UDP 埠中一端要能被連到低系統元件沒有第三方；開的那個埠對沒鑰匙的人是「靜默」的（不回應）。跨網段時最推薦墊在下面；同一個區網不需要。
MQTT（自架 Mosquitto）是broker 要能被連到中broker 在哪就看哪低paho-mqtt、brokerIoT 的通用語言：感測器、ESP32、樹莓派都會講。但 broker 本身是一台要架的伺服器、要管 TLS／帳密；對「兩台電腦互派任務」是殺雞用牛刀。留作第三種傳輸層（感測器多了再做）。
區域網路 TCP ＋ 信封是主控台在內網開一個埠低同網段才行毫秒無（標準函式庫）哨兵主動連主控台（哨兵不用開埠）；沒驗過的連線什麼都做不了。最簡單、最快；跨網段就墊 WireGuard。已做。
共用資料夾 ＋ 信封是是最低看資料夾怎麼同步秒級（輪詢）無NAS 分享、Syncthing、甚至 USB 都行；不開任何埠、不連外。慢一點但零設定。已做。
SSH 隧道是一端開 22中一端要能被連到低sshdWindows 要裝 OpenSSH Server、管金鑰；比 WireGuard 沒好處。
ZeroMQ（CurveZMQ）／gRPC mTLS是要開埠中高同上低pyzmq／grpcio做得到一樣的事，但多一個大相依，信封層的安全還是得自己管（Curve 只保護連線）。
Matrix／XMPP 自架是伺服器要開高是秒級很多為了兩台電腦架一個聊天伺服器，太重。

結論。同一個區網：TCP。開不了埠或想完全不連網：共用資料夾。跨網段：WireGuard 墊在 TCP 下面（WireGuard 本身就是「只有鑰匙對的人才存在」的設計，跟信封的精神一致）。這三條都不靠第三方、都不碰公網、都用同一套信封與同一套程式。

04 · 推薦架構（已實作）

每一層只認識下一層；角色與指令只碰事件匯流排，不碰傳輸層；傳輸層看不到明文。

為什麼哨兵「主動連」主控台

哨兵常常是樹莓派、放在門口的小電腦、別人家的機器；它們不用開埠、不用固定 IP，只要能出去。主控台只要在內網開一個埠。斷線哨兵自己退避重連。

為什麼不是 HTTP／WebSocket

信封已經是完整的安全層，HTTP 只會多一層框架與一堆標頭要過濾。4 bytes 長度前綴的 TCP 框架加上 1 MB 上限，整段程式一百行、沒有新相依。要走瀏覽器時再加 WebSocket 傳輸。

為什麼哨兵以「自己的擁有者」身分跑

主控台那邊是誰下的，哨兵看不到也不信；信任的邊界是名單（配對），不是人。跑的路跟排程觸發一模一樣（via=ROUTINE、同一個 authorize），再加一道 max_effect 上限。

為什麼名單與任務簿放保管箱

名片本身不是祕密，但被改成攻擊者的公鑰就等於換掉對方；保管箱的 HMAC 擋得住改檔。data/ 本來就是信任邊界。

05 · 安全設計

身分

每台一組長期金鑰：Ed25519（簽章、身分）＋ X25519（金鑰交換），存保管箱 link_identity。node_id ＝ SHA-256(簽章公鑰) 前 12 bytes，寫成 3f2a-9c1e-… 六組。名片（NodeCard）是兩把公鑰＋名字，由 Ed25519 簽過，所以拿到名片就能確認兩把鑰匙是同一台的。不做 Ed25519→X25519 轉換（cryptography 沒提供，兩把分開也比較乾淨）。

信封

{"v":1, "from":"寄件者", "to":"收件者", "seq":12, "ts":1760000000,
 "eph":"一次性 X25519 公鑰", "salt":"16 bytes", "ct":"密文", "sig":"Ed25519 簽章"}

shared = X25519(eph_priv, peer_box_pub) ‖ X25519(my_box_priv, peer_box_pub)
key    = HKDF-SHA256(shared, salt, info = "synox-link-v1|from|to")      # 每封一把
ct     = ChaCha20-Poly1305(key, nonce = 0, plaintext = {"kind","body"}, aad = 表頭)
sig    = Ed25519(寄件者簽章私鑰, aad ‖ ct)
  • 第一段 DH 用一次性金鑰：之後私鑰外洩，舊信也解不開（前向保密）。
  • 第二段 DH 用寄件者長期金鑰：只有寄件者或收件者算得出 key，收件者因此知道是誰寄的。
  • 簽章再確認一次寄件者，而且收件者可以留存證據（主控台的任務簿）。
  • 每封換 key 所以 nonce 固定全零是安全的；這避開了 96-bit 隨機 nonce 的碰撞問題，也不用 XChaCha。
  • to／seq／ts 都在 AAD：改收件者、改序號、改時間都驗不過。

重放與順序

三道：ts 與現在差超過 5 分鐘＝拒（兩台時鐘要大致對）；同一寄件者的 seq 只能往上（寄件計數與「上次看到的」都存保管箱，重開程式不會倒退）；5 分鐘視窗內看過的 (from, salt) 不收第二次。

配對

主控台 python -m synox link pair 印一行配對碼 ＝ 主控台名片 ＋ 16 bytes 一次性祕密，10 分鐘有效。哨兵 link join 存起來，跑起來時送 pair.request：信封本身已經是封給主控台的（哨兵有主控台名片），自己的名片放在信封的 card 欄位，body 帶 HMAC-SHA256(祕密, 哨兵名片 ‖ 主控台 node_id)。主控台只在「正在等配對碼」時才看 card，mac 對了才把哨兵寫進名單並回 pair.ok；錯了不回任何東西。沒有網路也能配：兩邊 link card 印名片、link trust 互貼（SSH 式）。

威脅表

攻擊者拿到／能做結果
在區網上看封包、改封包、重送封包看到密文；改一個字簽章與 AEAD 都失敗；重送被 seq／salt／ts 擋。
連上主控台開的 TCP 埠送什麼都被丟掉（不回應），三次就斷線；最多 32 條連線。等於 WireGuard 的「靜默」。
10 分鐘內拿到配對碼能以哨兵身分進名單：主控台之後可能派任務給它、它會看到派來的指令文字。它拿不到主控台的資料、不能對主控台下指令。
拿到哨兵的 data/等於那台哨兵（跟現在拿到 data/ 一樣）；可以冒充那台回報結果。主控台 /link_forget 就斷。
拿到主控台的 data/ 或主控台被攻破所有哨兵都聽它的（在各自 max_effect 之內）。主控台要是最信任的那台。
共用資料夾被別人寫入寫進去的東西驗不過就被刪掉；可以塞滿磁碟（沒做配額）。
哨兵被攻破只影響派給它的任務；它可以回假的結果。主控台不會因為哨兵回了什麼而執行任何東西（結果只是文字）。

老實清單。TCP 沒有 TLS（靠信封；對外聽的埠只建議內網或 WireGuard 裡）。沒有 NAT 穿透。沒有流量整形（folder 傳輸可以被塞滿）。密碼學是標準原語的標準組合（跟 libsodium 的 sealed box ＋簽章同構），但沒有經過獨立審查；程式只在開發機以記憶體傳輸、socketpair、127.0.0.1 的 TCP 驗過。

06 · 任務協定與交接

信封 kind方向body
task.offer主控台 → 哨兵{id, command, lineage, context, attempts}
task.accepted／task.rejected哨兵 → 主控台{id}／{id, reason}（reason 是給人看的一句：「這台沒有這個指令」「效果 danger 超過 max_effect」…）
task.progress哨兵 → 主控台{id, text}（協定有、哨兵現在還沒有人送）
task.result哨兵 → 主控台{id, ok, text, error}；text 是指令的回覆全文（最多 8000 字）
task.cancel主控台 → 哨兵{id}（盡力：已經開始做的做完但不回結果）
hello／heartbeat／ping／pong雙向連上時、每 30 秒、探測
pair.request／pair.ok哨兵 → 主控台 → 哨兵配對（見 05）

交接（handoff）的做法刻意簡單：主控台把 A 的結果放進新任務的 context（from_task、from_worker、result）派給 B。哨兵之間不直接講話；主控台永遠是唯一的協調者，所以信任圖是一顆星，不是網。要讓 B 真的「用到」A 的結果，B 的那個指令要自己讀 context（下一步：讓哨兵把 context 放進子程序的環境變數或 AI 的系統提示）。

07 · 事件匯流排（observer）

每台 SYNOX 一個 EventBus：主題是用點分的字串，subscribe(pattern, handler) 用 fnmatch（task.*、link.in.*、*），同步呼叫、handler 例外隔離、有 wait_for。收到的信驗過之後一律變成 link.in.<kind>；角色再把它翻成領域事件。

主題誰發事件內容
link.in.<kind>LinkNodemsg（Message：kind、body、sender、seq、ts）、peer、conn
link.out.<kind>LinkNodepeer、kind、sent（傳輸層有沒有送出去）
link.rejectedLinkNodepeer、reason（驗不過的信：陌生寄件者、重放、簽章…）
link.peer.online／offline、link.pairedLinkNodepeer（在線狀態改變；配對成功）
task.offered／running／progress／done／failed／rejected／cancelledConsoleRoletask（整個 Task 的 dict）
worker.accepted／rejected／done／failedWorkerRoleid、command、text／error
# 之後要做的自動化都長這樣：不碰傳輸、不碰角色
link = app.extras["synox_link"]
link.bus.subscribe("task.failed", lambda topic, e: link.console.redo(e["task"]["id"])
                                                   if e["task"]["attempts"] < 3 else None)
link.bus.subscribe("link.peer.offline", lambda topic, e: app.notify_owner(f"⚪ {e['peer']} 離線了"))

跟 SDK 現有的 DispatchObserver 是兩回事：那個看的是「這台 dispatcher 跑了哪個指令」，這個看的是「兩台之間發生了什麼」。哨兵跑指令時仍會經過 dispatcher，所以 SDK 的 observer 也看得到（kind＝command、channel＝link）。

08 · 不在同一個網段時

WireGuard（推薦）

主控台那邊開一個 UDP 埠（或兩邊都在同一個 WireGuard 網裡），哨兵的 config 寫 WireGuard 位址。WireGuard 對沒鑰匙的人不回應，跟信封的精神一樣；Windows 有官方客戶端，樹莓派是核心內建。沒有第三方。

共用資料夾經 Syncthing

兩台各自跑 Syncthing 同步一個資料夾（Syncthing 的發現伺服器是第三方，但可以關掉只用手動位址）。零埠、零固定 IP，但是秒級到分鐘級的延遲。

只開一個埠到公網（不建議但可以）

主控台 port-forward 8831，哨兵直接連。沒驗過的封包全被丟，理論上撐得住；但那是公網上一個會回 TCP 握手的埠，比 WireGuard 多露一點。要做就加 Noise 握手讓沒鑰匙的人連 ACK 都拿不到。

之後：自架小 relay

兩台都主動連一台你自己的小 VPS（它只搬密文、看不懂內容），就是「不信任的中繼」。信封設計已經允許這件事，只要寫一個 relay 傳輸。沒有做，因為擁有者現在不想多一台伺服器。

09 · IoT：攝影機、Arduino、樹莓派

硬體都掛在哨兵身上、當那台的 pack（kind=cli 或 kind=python），主控台只會 /link_run 門口 /cam_snap。這樣硬體的安全邊界跟現在的 pack 一樣（五關、沙盒、容器），link 不用為它們另外設計。

要做的事Python 怎麼接放哪備註
USB 攝影機拍照opencv-python：cv2.VideoCapture(0) → read() → imwrite哨兵的 cli pack（requires.pip 釘版本）Windows／Linux 都行；影像檔用 pack.path_of 放資料夾，回覆走 send_photo（link 現在只回文字，圖片要下一步）
樹莓派 CSI 攝影機picamera2（libcamera）樹莓派哨兵的 python packPi OS Bookworm 以後用 picamera2，不是舊的 picamera
Arduino 開關、讀感測器pyserial ＋ Arduino 跑 StandardFirmata → pyfirmata2；或自訂簡單的序列協定哨兵（USB 線接著的那台）序列埠是最簡單的硬體介面；沙盒要把 /dev/ttyUSB0／COM 埠放行
樹莓派 GPIOgpiozero（Pi 5 用 lgpio 後端）樹莓派哨兵繼電器、LED、按鈕一行搞定
一堆感測器／ESP32MQTT（自架 Mosquitto；paho-mqtt）哨兵訂閱 broker，或 link 多一個 MQTT 傳輸感測器多了再做；單台相機／Arduino 不需要
樹莓派當哨兵裝 Python 3.11+、pip install -e .、config 寫 link.role=worker、link.connect—程式本身跨平台；安裝精靈只有 Windows，Linux 手動裝；sandbox 後端用 bwrap／systemd-run

一個典型的擺法：客廳的 Windows 當主控台（有 Telegram、有 AI），門口的樹莓派當哨兵（相機、GPIO），書房的桌機當另一台哨兵（算力、檔案）。你在手機上說「看一下門口」，AI 在主控台叫 /link_run 門口 /cam_snap，門口那台拍照回傳。
