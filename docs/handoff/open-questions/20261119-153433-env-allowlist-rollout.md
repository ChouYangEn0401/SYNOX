# 子程序的環境變數白名單怎麼上線：一次擋，還是先一版只記錄

狀態：待處理（要維護者決定；沒決定＝照建議 A；不擋 [隔離階段 0～1 那張交辦單](../20261119-153431-windows-isolation-stage0-1.md) 開工）

## 問題一句話

「子程序只拿到白名單上的環境變數」（[ADR 0022](../../adr/0022-ecosystem-bridge-and-sandbox.md) 決定 16，**方向已決定**）上線的那一版，要直接擋掉白名單以外的變數，還是先一版只記錄「哪些工具用到了被擋的變數」、下一版才擋？

## 脈絡

- 現在子程序拿到 SYNOX 的整份環境變數，只拿掉名字像密鑰的（`vendor/isdtelekit/jobs/cli.py` 的 `clean_env()`）。這等於把使用者自己設的變數（例如 `PYTEST_ADDOPTS`、`GIT_*`、`PYTHONPATH`、`NODE_OPTIONS`、各種服務的設定）全交給第三方工具。
- 白名單＝系統必要的幾個＋pack 宣告的（`requires.env`、`cli.env`）＋SYNOX 自己給的（`SYNOX_*`、`PYTHONIOENCODING`）＋之後的代理設定。
- 風險：有些既有工具可能默默依賴某個沒宣告的變數（例如 `APPDATA`、`HOME`、語系、代理），一擋就壞，而作者要等下一版才補宣告。
- 白名單不需要隔離就做得到，所以對 Windows 的 `none` 後端也有效；它是「沒有沙盒時」少數能立刻加上的保護之一。
- 官方工具庫的工具都在同一個維護者手上，可以一起補宣告；第三方工具無法保證。

## 選項

| 選項 | 一句話 | 建議 |
|---|---|---|
| A | 一次套用到所有子程序工具；同一版附一個設定開關（例如 `policy.sandbox.env: "legacy"`）讓維護者在一版內可以整台退回舊行為，下一版拿掉開關 | ✅ 建議（預設做這個） |
| B | 先一版「只記錄」：照舊給整份環境，但記下每個工具實際讀了哪些白名單外的變數（做不到精確偵測，只能記「給了哪些」）；下一版才擋 | |
| C | 只對第三方（不是官方簽章）的工具套用；官方工具照舊 | |
| D | 一次套用、沒有退回的開關 | |

建議 A 的理由：方向已定，晚一版擋等於多一版把使用者的變數交出去；B 的「只記錄」在不改 vendor 的前提下其實看不到工具讀了什麼，資料價值低；
C 讓官方與第三方行為不同、比較難測；A 有退路，萬一某個工具壞了，維護者不用等新版就能先恢復。

## 驗收

- 選 A：白名單在每個後端（含 `none`）生效、有測試；設定開關有測試（開了＝舊行為、關了＝白名單）；`CHANGELOG.md` 寫明「哪個版本會拿掉開關」；官方工具庫的工具在白名單下測試都過。
- 選 B／C／D：照選項寫進 ADR 與測試；B 要寫清楚「下一版」是哪一版。

## 不要做的事

- 不要改 `vendor/isdtelekit/`（`AGENTS.md`）；白名單在 SYNOX 這一層做。
- 不要因為某個工具壞了就把那個變數加進「系統必要」：那個工具應該自己在 `pack.json` 宣告。
- 不要把密鑰類的變數加進白名單預設值。
